# Инструменты разработки

Скрипты, которые помогают готовить и проверять данные, но не входят в
сам плагин. Описание работы плагина и его настроек — в корневом
[README.md](../README.md).

| Скрипт | Что делает |
|---|---|
| `build_plugin.py` | собирает `dist/qgis_xtopo-<версия>.zip` и ставит плагин в профиль QGIS |
| `run_tests.sh` / `run_tests.py` | прогон тестов (`unittest`, offscreen) |
| `run_qgis.sh` | сборка + установка + запуск QGIS с открытой панелью |
| `check_pbf_coverage.py` | сверяет подготовленную выгрузку с эталоном osmium |
| `check_peak_placement.py` | проверяет положение пиков OSM по рельефу |
| `render_peak_review.py` | рисует фрагменты карты с изолиниями по CSV разметки |
| `make_peak_map.py` | собирает интерактивную карту пиков по CSV |
| `dem_compare_server.py` + `dem_compare.html` | сравнение наборов DEM между собой |

## Сравнение DEM-наборов

Инструмент для сравнения наборов высот между собой:
`tools/dem_compare_server.py` (сервер) и `tools/dem_compare.html`
(страница). Сервер отдаёт страницу и рисует тайлы рельефа через GDAL,
подтягивая исходники из публичных хранилищ.

```sh
python3 tools/dem_compare_server.py            # http://127.0.0.1:8765/
python3 tools/dem_compare_server.py --port 9000 --cache ~/qgis_projects/qgisxtopo-cache/dem_compare
python3 tools/dem_compare_server.py --temp-dir /mnt/data/temp/dem
python3 tools/dem_compare_server.py --local-dem ~/dem/my_tiles
python3 tools/dem_compare_server.py --local-dem ~/dem/a --local-dem2 ~/dem/b
```

`--cache` — постоянный кэш (тайлы, подготовленные окна, исходники), он не
удаляется. `--temp-dir` — каталог временных файлов: туда GDAL кладёт
промежуточные VRT и spill больших warp, там же лежит недокачанный `.hgt.gz`.
По умолчанию берётся системный временный каталог; если `/tmp` очищается при
перезагрузке, укажите постоянный путь.

`--local-dem` добавляет собственный каталог с рельефом набором «Свой рельеф»,
`--local-dem2` — вторым набором «Свой рельеф 2», чтобы сравнивать два своих
набора между собой. Каталог обходится рекурсивно, берутся GeoTIFF, HGT, VRT,
IMG, ASC и другие растры GDAL; охват каждого файла читается один раз при
индексации. Данные локальные, поэтому прогрев для таких наборов пропускается.

Sonny DTM скачивается с Google Drive целыми градусными тайлами: список
файлов общий с плагином (`~/.cache/qgis-xtopo/sonny/listings.json`), архивы
кладутся в `<cache>/sonny/<набор>`. Если списка ещё нет, сервер загружает
его при первом обращении. Тайлы 0,5″ для Австрии и Швейцарии читаются через
VRT-обёртку: драйвер SRTMHGT не понимает 7201 точку по стороне.

На странице каталоги выбираются кнопкой «выбрать каталог…» — открывается
обзор файловой системы сервера, папки с растрами помечены. Первый каталог
попадает в A, второй в B. Браузер не отдаёт веб-странице путь к локальной
папке, поэтому обзор делает сервер; он же слушает только 127.0.0.1.
В окне обзора можно вставить путь в поле ввода и нажать «перейти» — это
удобно для длинных путей и симлинков. Ошибка показывается в самом окне, а
кнопка «выбрать этот каталог» активна только после успешной загрузки пути.
Выбранные каталоги запоминаются в `<cache>/local.json` и `local2.json` и
восстанавливаются при следующем запуске сервера, поэтому открытая страница
с `a=local` не получает 404 после перезапуска.
Файлы с именами 1°-тайлов (`N46E009.tif`) индексируются по имени, без
открытия растров, поэтому каталог-симлинк на медленном sshfs-монтировании
не ждёт чтения метаданных каждого файла; остальные растры открываются для
определения охвата, а у симлинков разрешение по умолчанию 30 м и уточняется
при рендере.

### Предварительный прогрев

Чтобы страница открывалась без ожидания сети, кэш можно наполнить заранее:

```sh
python3 tools/dem_compare_server.py --precache
python3 tools/dem_compare_server.py --precache --jobs 16
python3 tools/dem_compare_server.py --precache --precache-view 1600x1000
python3 tools/dem_compare_server.py --precache --precache-margin 3
python3 tools/dem_compare_server.py --precache --precache-tiles
```

Прогрев берёт список точек из `dem_compare.html` и для каждой точки и набора
скачивает исходные данные в локальный кэш. Сервер при этом не запускается.
**Тайлы по умолчанию не рисуются**: когда данные уже лежат локально, один
тайл считается за десятые доли секунды, а скачивание области — это секунды
и десятки мегабайт. Поэтому прогреваем только сеть, а картинку страница
получает по требованию. `--precache-tiles` дополнительно рисует тайлы — это
нужно, только если показ должен работать вообще без обращений к сети.

Области готовятся параллельно (`--jobs`, по умолчанию 8 потоков): узкое
место — сеть, поэтому потоки заметно ускоряют первый запуск. Для SRTM
скачиваются `.hgt.gz` и сохраняются как GeoTIFF (`<cache>/srtm3`), для
Sonny — zip-архивы градусных тайлов (`<cache>/sonny/<набор>`), для
COG-наборов вырезается окно области в родном разрешении
(`<cache>/prepared/vN/<набор>`): целиком такие файлы не качаются. При
`--precache-tiles` готовые тайлы кладутся в `<cache>/tiles`, промежуточный
DEM — в `<cache>/dem3857`. После прогрева страница открывается мгновенно, а
`/api/status` показывает нули в очереди.

Область вокруг точки берётся с запасом в два тайла (`--precache-margin`):
окно страницы бывает больше стандартного, и без запаса крайние тайлы уходили
в сеть. Запас можно увеличить, если вы часто сдвигаете карту. Режимы
(`--precache-modes`, по умолчанию `hillshade,elevation,contours`) имеют
значение только вместе с `--precache-tiles`.

Тайлы вне прогретой области сервер тоже не тянет из сети по одному: при
первом промахе он сохраняет локальный блок вокруг тайла (примерно
1024 пикселя источника, около 0,28° для 30-метровых наборов) и переиспользует
его для соседей. Первый тайл такого блока стоит несколько секунд, остальные
читаются из кэша. Старые автоблоки удаляются, когда их набирается больше
160 на набор.

Ниже z9 новые исходники не загружаются вообще: ни тайлы Sonny/SRTM, ни
окна COG через STAC и `/vsicurl`, ни даже список файлов Sonny. Сервер
использует только то, что уже лежит в кэше (скачанные тайлы, прогретые
окна), поэтому высота под курсором может быть известна, но новых файлов
не появляется.
Отсутствующие тайлы (у GLO-30 часть не опубликована) запоминаются на час:
первый запрос стоит доли секунды, дальше сервер сразу отвечает «нет данных»,
а страница просто не рисует этот тайл вместо ошибки 500.

Объём кэша для всех 16 точек — несколько гигабайт; файлы не удаляются,
повторный прогрев использует уже скачанное. Прогрев можно прервать
(Ctrl+C) и запустить снова: готовые области и тайлы пропускаются.

После запуска сервер печатает ссылку на страницу, путь к кэшу и подсказку,
как остановить. Если порт занят, он скажет об этом и предложит другой.

Страница показывает, что происходит, в статусной строке внизу окна, во всю
ширину — она идёт и под боковой панелью: координаты и высоты под курсором с
разницей наборов, полоски загрузки тайлов по A и B, разрешение источника и
текущий масштаб. На узком окне строка переносится на две-три, а не наезжает
элементами друг на друга: полоски прогресса и подписи остаются на своих
местах. Пока сервер тянет исходные данные из сети, строка
показывает, что именно качается и сколько это уже длится: «Copernicus
GLO-30 · N50E100 · 7 с». Метка — набор и градусный тайл той гранулы,
которую читают; при сравнении двух наборов видны оба, остальные
сворачиваются в «+N». Служебные запросы к Planetary Computer тоже видны:
«· список файлов» и «· токен доступа». Загрузка показывается и во время
расчёта шкалы высот — это как раз самый долгий случай. Состояние сервера
отдаёт `/api/status`, страница опрашивает его раз в секунду.

Боковую панель можно свернуть кнопкой «свернуть» в её верхней части — карта
занимает всё окно, а кнопка `»` в левом верхнем углу возвращает панель. Список ключевых точек сворачивается отдельно,
кликом по его заголовку. График профиля стоит сразу под ключевыми точками.
Пояснение «Как читать» свёрнуто в заголовок и раскрывается по клику — на
главном экране оно занимает одну строку. Точки сгруппированы по регионам (Канада, США,
Мексика, Южная Америка, Европа, Россия, Азия, Африка, Австралия, полярные
регионы) и отсортированы по алфавиту внутри группы; по умолчанию видны
первые пять пунктов, остальные открываются кнопкой «ещё» внизу списка. Оба
состояния запоминаются в браузере. Кнопки «профиль», «1:1», «OSM» и
ползунок доли рельефа вынесены в отдельную полосу над боковой панелью,
шириной с неё.

Наборы — все с разрешением 1″ (30 м) или лучше:

| Ключ | Набор | Источник | Покрытие | Вертикаль |
|---|---|---|---|---|
| `srtm3` | SRTM v3 | AWS `elevation-tiles-prod` (skadi) | глобально | EGM96 |
| `cop30` | Copernicus DEM GLO-30 | AWS `copernicus-dem-30m` | суша, часть тайлов не отдана | EGM2008 |
| `fabdem` | FABDEM v1.2 | Hugging Face, COG-зеркало LINKS | −60°…+80°, DTM без леса и застройки | EGM2008 |
| `nasadem` | NASADEM HGT | Planetary Computer | −56°…+61° | EGM96 |
| `alos30` | ALOS World 3D-30m | Planetary Computer | глобально | EGM2008, DSM с лесом |
| `3dep` | USGS 3DEP Seamless (1/3″) | Planetary Computer | США, Канада, Мексика | NAVD88, DTM |
| `sonny` | Sonny DTM LiDAR (1″, 0,5″) | Google Drive | Европа | национальные, DTM |

### Охват наборов

С z4 до z9 страница рисует контрастные границы охвата выбранных наборов
A и B (сплошная линия с тёмной обводкой и полупрозрачная заливка).
Охват считается по именам 1°-тайлов: у Sonny — из каталога Google Drive,
у SRTM — по диапазону 56° ю.ш. — 60° с.ш., у COG-наборов — из STAC
(запрос по видимой области, запрашиваются только `id` и `bbox`). У
локальных каталогов показываются охваты файлов. Если набор покрывает
весь экран, границы не рисуются: они совпали бы с его краем, но видна
заливка всего окна. Слой выключается галочкой «охват наборов» в боковой
панели.

FABDEM — единственный набор с некоммерческой лицензией (Non-Commercial
Government Licence v2.0): он годится для личной проверки, но не для
коммерческого использования. Остальные наборы — открытые данные.

Страница умеет: переключать наборы A и B на лету, сравнивать их шторкой с
перетаскиваемой границей, показывать разность высот B − A, строить профиль
по двум точкам, рисовать отмывку, гипсометрию и горизонтали, приближать до
пикселя источника (кнопка «1:1») и показывать высоту под курсором с
разницей между наборами. Профиль интерактивен: наведение на график ставит
точку на линии профиля на карте, наведение на линию — на графике; легенда
подписывает кривые как A и B. Смена набора A или B пересчитывает профиль по
той же линии, у графика адаптивная сетка: линии по высоте и по расстоянию
ложатся на круглые значения, границы диапазона подписаны. Под графиком
пишется разница высот B − A, окрашенная как дельта на карте (красным вверх,
синим вниз, светлее — иначе мелкая дельта на тёмном фоне не читается):
при наведении — разница в текущей точке, без курсора — средняя
по линии. После выбора второй точки панель прокручивается к подписи под
графиком: она появляется только после расчёта профиля, и прокрутка к началу
графика оставляла её за нижним краем панели. Состояние (наборы,
режим, центр, зум) пишется в
адрес страницы — ссылкой можно поделиться. В поле «Ссылка OSM» можно
вставить ссылку OpenStreetMap (`#map=зум/широта/долгота`, `mlat`/`mlon`,
`geo:` или пару координат): страница возьмёт из неё центр и зум. Короткие
ссылки `osm.org/go/…` раскрывает сервер.

Под рельефом лежит подложка OpenStreetMap. Она всегда непрозрачная, а
рельеф рисуется поверх неё с заданной долей: так видно, куда сдвинута карта
и что находится рядом. Кнопка «OSM» в полосе над боковой панелью включает и
выключает подложку; когда она включена, ползунок «рельеф» задаёт долю
рельефа поверх неё: 0 % — только OSM (тайлы рельефа не запрашиваются),
100 % — рельеф полностью перекрывает подложку. При выключенной подложке
рельеф непрозрачный. Состояние пишется в адрес. Тайлы OSM
запрашиваются через локальный сервер и кэшируются в `<cache>/osm`,
поэтому повторные просмотры не ходят в сеть.

Поверх рельефа пунктиром показаны границы градусных тайлов 1×1° с подписью
в левом верхнем углу (`N45E007`, `S03W062`) — так же называются исходники
SRTM и Copernicus, по сетке видно, из какого тайла взяты данные. Подпись
обозначает весь тайл: как в именах файлов, угол тайла — юго-западный, поэтому
подпись стоит над своим тайлом, а не под ним. Линии и подписи тёмно-красные,
у подписей мягкий светлый ореол вместо контрастной обводки.

В режимах «высоты» и «горизонтали» цвет зависит от шкалы, поэтому пределы
общие для всего видимого экрана и для всех наборов сразу: иначе соседние
тайлы и половины шторки окрашивались бы по разным шкалам. Пределы считает
сервер (`GET /api/limits?ds=…&z=…&x0=…&x1=…&y0=…&y1=…`) по видимым тайлам,
округляет наружу до круглых чисел — небольшой сдвиг карты шкалу не меняет —
и страница передаёт их в запрос тайлов (`&lo=…&hi=…`). Шаг горизонталей
считается по тому же видимому размаху. Пересчёт — при отпускании мыши и при
смене режима или наборов; во время перетаскивания тайлы рисуются по прежней
шкале. Тайлы с разными пределами лежат в кэше в разных каталогах
(`<cache>/tiles/v7/<набор>/<режим>/r<lo>_<hi>/`), иначе отдался бы PNG,
нарисованный по чужой шкале.

Пока шкала считается, в строке статуса горит «считаем шкалу высот…»: сервер
считает пределы по DEM и может докачивать набор минутами. Если в это время
идёт загрузка, вместо этой надписи показывается, что именно качается, — она
важнее. Тайлы в этих
режимах до получения шкалы не запрашиваются — иначе они попали бы в кэш без
пределов. Запрос пределов повторяется сам, пока ответ не придёт; при ошибке
сервера показывается её код, а не молчание.

Ниже зума 9 рельеф не рисуется: на таких масштабах тайлы слишком обобщены,
и остаётся только подложка OSM — по ней и выбирают место, а рельеф
включается при приближении. В этом режиме кнопка «OSM» заблокирована,
ползунок доли рельефа тоже, а сервер не начинает новых загрузок рельефа:
запросы высоты и профиля он обслуживает только по уже закэшированным
данным.

Исходники не качаются целиком: COG читаются по HTTP Range (`/vsicurl`),
только нужные блоки. Сжатый SRTM `.hgt.gz` приходится скачивать целиком и
разворачивать в GeoTIFF. FABDEM тоже COG, но ссылка Hugging Face
перенаправляет на подписанный адрес CDN — GDAL проходит это сам.
После `--precache` блоки COG не нужны: окно
области уже лежит в `<cache>/prepared` и читается с диска. Отрисованные
тайлы тоже кэшируются (`<cache>/tiles`) и не удаляются: повторный запуск
мгновенный.

Файлы Planetary Computer подписываются одним SAS-токеном на контейнер, а не
по одному: сервис подписи при параллельных запросах отвечает 429, и тайл
ждал по 80 секунд. Одновременных перепроекций не больше шести
(`DEM_COMPARE_SLOTS`), а тайл 256×256 считается без многопоточности: на
таком размере потоки только конкурируют за кэш GDAL.

Тайлы запрашиваются пачками (`GET /tiles?ds=&z=&mode=&lo=&hi=&t=x,y…`):
браузер держит не больше шести соединений на хост, и поштучные запросы
оставляли половину слотов рендера простаивать. Сервер рисует пачку в общем
пуле и отдаёт кадры `DEMFRAME x y status seconds length` и сразу за ними
PNG по мере готовности, поэтому медленный тайл не задерживает остальные.
Выигрыш заметен, когда слотов больше шести: с `DEM_COMPARE_SLOTS=12` экран
отмывки приходит примерно в полтора раза быстрее, а на готовых PNG из кэша
разницы почти нет — там всё упирается в отдачу.

Два экземпляра сервера на одном кэше не мешают друг другу: временный файл
подготовки области именуется с PID и потоком. Раньше имя было общим, и один
процесс переименовывал файл, который второй уже удалил, — запрос падал с
500. Ошибка одного тайла больше не роняет расчёт шкалы целиком.

Рендер устроен так: источник сразу переводится в Web Mercator (тайл
256×256, float32), отмывка считается в numpy с поправкой на cos(широты) —
в Mercator шаг по долготе короче наземного. Горизонтали — тоже массивами
numpy: маска ищет пиксели, где расстояние до ближайшего уровня меньше
половины перепада высоты на пиксель, поэтому тайлы считаются параллельно
и не держат GIL. Промежуточный растр DEM
кэшируется (`<cache>/dem3857`), открытые COG-датасеты остаются открытыми,
поэтому GDAL держит их блоки в своём кэше: первый тайл новой области тянет
данные из сети (5–10 с), соседние тайлы той же области — мгновенно.
Страница не очищает холст, пока тайлы едут: под ними остаётся прошлый
кадр, поэтому при смене зума картинка не рассыпается на квадраты, а
показывает счётчик загруженных тайлов.

Про вертикальные системы: SRTM/NASADEM — EGM96, Copernicus/ALOS — EGM2008,
3DEP — NAVD88, Sonny — национальные системы (обычно над уровнем моря).
Смешивать наборы с разными системами в одном проекте нельзя: на границах
тайлов появляются ступеньки в несколько метров.

Лицензии: SRTM и 3DEP — public domain, NASADEM — NASA free and open policy,
Copernicus DEM — бесплатно для всех, включая коммерческое использование, с
ссылкой «Produced using Copernicus data and information funded by the
European Union and ESA», AW3D30 — бесплатно, но нужна ссылка на JAXA, а для
коммерческого использования требуется уведомить JAXA заранее. Sonny DTM —
CC BY 4.0, ссылка на sonny.4lima.de.

### Что показывает инструмент про полноту наборов

- **NASADEM** не заходит выше 61° и ниже −56° — на Шпицбергене высоты нет.
- **Copernicus GLO-30** не отдаёт тайлы Армении, Азербайджана, СЗ Ирана и
  Туркменистана (38–41° с. ш., 43–50° в. д.) — там только GLO-90.
- **3DEP** покрывает США, Канаду и Мексику.
- **Sonny DTM** — только Европа; 0,5″ есть лишь для Австрии и Швейцарии,
  остальное — 1″.
- **SRTM v3** занижает вершины на крутых склонах: на Маттерхорне он даёт
  3602 м, Copernicus GLO-30 — 4229 м.

## Проверка положения пиков

Ошибочный пик — узел `natural=peak`, поставленный не на гребне, а в долине
или на склоне: на карте он подписывается высотой из `ele_calc` (значение DEM
в точке), но вершины в этом месте нет. `tools/check_peak_placement.py`
проверяет пики без названия в двух категориях — без `ele` и с `ele`
(узлы с названием не трогаем).

Пик считается ошибочным, если он не на вершине и не на хребте. Правило —
набор пар признаков: ошибка отмечается, если сработала хотя бы одна пара.
Одиночное условие не годится: «нет острого гребня в 100 м» срабатывает и
на настоящих круглых вершинах. Срабатывает любое из:

* дальше 50 м от строгого водораздела и поперёк склона в 900 м рельеф выше
  на 120 м — пик на дне долины;
* нет острого гребня: перепад 25 м на 150 м дальше 250 м и перепад 15 м на
  450 м дальше 40 м;
* перепад 25 м на 150 м дальше 90 м и ближайшая вершина рельефа дальше 600 м
  — вокруг пологое место, а вершины рядом нет;
* пик не на гребне (обе стороны ниже на 20 м) и провал в 200 м больше 170 м;
* выше точки больше 65 % кольца в 1200 м и провал в 300 м больше 120 м;
* выше точки больше 45 % кольца в 700 м и провал в 450 м больше 350 м;
* провал в 200 м больше 240 м и ближайшая вершина дальше 300 м;
* провал в 600 м больше 50 % местного рельефа и ручей не дальше 200 м — пик
  в долине;
* высота OSM выше рельефа более чем на 4 % и провал в 450 м больше 500 м —
  пик сдвинут вниз от настоящей вершины;
* ближайшая вершина рельефа дальше 600 м, а более высокий пик OSM — дальше
  1400 м: пик стоит на пологом участке под настоящей вершиной;
* высота OSM и рельеф расходятся более чем на 10 % — пик поставлен не на ту
  вершину.

Признаки — по выбранному рельефу, высоте из тега OSM `ele` и положению
соседних пиков OSM. Источник задаётся `--dem-source` (все наборы плагина:
`srtm`, `cop30`, `nasadem`, `alos`, `3dep`, `manual`). Для ALOS, Copernicus
и NASADEM автоматически включается профиль порогов
(`SOURCE_THRESHOLD_PROFILES` в `core/peak_placement.py`): их поверхность
сдвигает метрики, и базовые пороги ловят верные пики. Профиль отключается
`--no-source-profile`. Пороги подобраны перебором на 95 пиках, размеченных
вручную: SRTM 0 ложных / 46 из 49, ALOS 0 / 37, Copernicus 2 / 38,
NASADEM 1 / 39.

То же правило применяется при подготовке карты (`core/peak_filter.py`):
безымянные пики с вердиктом `error` удаляются из `peak.sqlite`, а у
остальных безымянных пиков `ele` заменяется на высоту рельефа при
расхождении больше 10 %. Расхождение высоты само по себе пик не удаляет.
Краткая статистика выводится в журнал плагина.

```sh
python3 tools/check_peak_placement.py \
    --pbf ~/qgis_projects/qgisxtopo-cache/geofabrik/georgia.osm.pbf \
    --out /tmp/peaks
```

Пороги настраиваются (`--far-divide`, `--valley-cross900`,
`--no-steep-crest`, `--no-crest-450`, `--smooth-150`, `--summit-far`,
`--off-ridge`, `--ridge-drop`, `--valley-ring-wide`, `--pit-drop`,
`--valley-ring-soft`, `--valley-drop-high`, `--far-drop`, `--near-max-d`,
`--ring-600-relative`, `--stream-distance`, `--ele-below`, `--shift-drop`,
`--neighbour-nearest`, `--ele-diff`). Расчёт рельефа идёт в нескольких
процессах (`--jobs`). Позиции пиков скрипт не меняет: это только выявление.

В Гималаях DEM SRTM завышен на сотни метров (у 43 % пиков DEM выше OSM
`ele`), поэтому часть признаков нормирована на местный рельеф, а не задана
в метрах, и сверка высоты из OSM с рельефом работает отдельно.

`tools/render_peak_review.py` рисует по CSV фрагменты карты с изолиниями,
реками из OSM, подсветкой гребней, проверяемым пиком (красный) и ближайшим
локальным максимумом рельефа (зелёный), складывает PNG и `index.html`.
Рендер параллельный (`--jobs`), реки и таблица читаются один раз.

```sh
python3 tools/render_peak_review.py --csv /tmp/peaks/peaks.csv \
    --pbf ~/qgis_projects/qgisxtopo-cache/geofabrik/georgia.osm.pbf \
    --out /tmp/peaks/maps --limit 60 --category anonymous
```

`tools/make_peak_map.py` собирает интерактивную карту на подложке
OpenTopoMap: тайлы запрашиваются локальным сервером по мере просмотра,
скачиваются через SOCKS5 и кэшируются, поэтому в браузере прокси не нужен.
`--csv` можно указать несколько раз — регионы сводятся на одной карте,
переключаются кнопками сверху, зум от 7 до 18.

```sh
python3 tools/make_peak_map.py --csv /tmp/peaks/peaks.csv \
    --out /tmp/peaks/map --serve --proxy socks5://127.0.0.1:1122
```

Недостающие тайлы SRTM скрипты докачивают в тот же кэш, что и плагин
(`~/qgis_projects/qgisxtopo-cache/srtm`).

## Проверка полноты данных

`tools/check_pbf_coverage.py` сверяет подготовленную выгрузку с эталоном
osmium: сравниваются множества `@id`, расхождение ~0,06% на границе
области.

```sh
QT_QPA_PLATFORM=offscreen python3 tools/check_pbf_coverage.py
```

Эталон — osmium вырезает область той же стратегией и тем же запасом, что
и плагин, и раскладывает объекты по слоям тем же движком запросов.

Список участков (квадраты 10x10 км) задаётся в начале файла. Проверено на
восьми участках — Грузия, Северный Кавказ, Юра, Саксония, Аляска, Корсика,
граница двух выгрузок и Малопольша: суммарно теряется около 0,06% объектов
(как правило, единичные здания и узлы на границе области). Основной источник
потерь — грубый фильтр GDAL: увеличение запаса фильтра их не убирает.

Кэш Geofabrik при этом должен быть скачан в
`~/qgis_projects/qgisxtopo-cache/geofabrik`.
