## 1. Критичные дефекты

### 1.1. `area_m2` не заполняется — фильтры шаблона работают неправильно

**Где:** `core/project.py:201`, `core/pipeline.py:1985`, `core/area_field.py:158`.

`run_project()` запускает поток источника и сразу вызывает
`project.prepare_project(config)`. Внутри `prepare_project()` вызывается
`ensure_area_fields(config.vector_dir)`, но в этот момент `stage/vector`
ещё пуст: слои создаются только позже, в `pipeline.run()`.

Проверка на синтетическом проекте `building`:

```text
project .../area/area.qgz
building.sqlite: ['ogc_fid', 'building', '@id', 'GEOMETRY']
```

Поля `area_m2` нет.

Последствия:

- в `automap.qgz` уже **69 фильтров** используют `"area_m2"`;
- правила без `ELSE` перестают отбирать объекты;
- правила с `ELSE` уходят в «крупный» символ;
- заявленная оптимизация (SQL-фильтр вместо `$area` на каждый объект) не работает;
- старые подготовленные проекты после обновления плагина тоже не получают поле:
  `repair_project()` его не добавляет.

**Исправление:**

- вызывать `area_field.ensure_area_fields(config.vector_dir)` в `run_project()`
  после `coastline`/`polygon_overlaps` и до `clean_project_layers()`;
- убрать вызов из `prepare_project()` или сделать его безопасным no-op;
- добавить end-to-end тест: `run_project()` → в `building.sqlite` и
  `water_dissolved.sqlite` есть непустой `area_m2`;
- для старых проектов — миграция в `repair_project()` или временный fallback
  на `$area` в фильтрах.

### 1.2. `NameError` в оценке PBF

**Где:** `core/pbf_source.py:1130` (сигнатура `_count_features`) и
`core/pbf_source.py:1167` (обращение к `bbox`).

```python
def _count_features(dataset, definitions, index, bbox_geometry, cancel,
                    progress, filtered, seen):
    ...
    area = (bbox.lon_min, bbox.lon_max, bbox.lat_min, bbox.lat_max)
```

Параметра `bbox` нет. Ошибка возникает после полного чтения файла, то есть
всегда, когда `probe_dataset()` доходит до конца.

Воспроизведение:

```sh
QGIS_XTOPO_TEST_PBF=/path/to/small.osm.pbf \
QT_QPA_PLATFORM=offscreen /usr/bin/python3 -m unittest \
  tests.test_pipeline_integration.PipelineIntegrationTest.test_pbf_probe
```

Наблюдалось:

```text
NameError: name 'bbox' is not defined
Ran 1 test ... FAILED (errors=1)
```

Затрагивает `PbfProbeWorker`, когда `probe_fast()` не поддерживает формат
(например, `.osm` или нестандартное сжатие): панель показывает «Не удалось
оценить PBF» вместо количества объектов.

**Исправление:** передать `bbox` в `_count_features()` из `_probe_source()`
или вычислить `area` из `bbox_geometry`. Тест `test_pbf_probe` по умолчанию
пропускается без `QGIS_XTOPO_TEST_PBF` — включить его в обычный прогон
или добавить unit-тест с mock-датасетом.

## 2. Высокий риск

### 2.1. `extracts.download_file`: до 5000 запросов и потеря готового файла

**Где:** `core/extracts.py:164-294`, особенно `218-289`.

Проблемы:

1. `total` обновляется только из `Content-Range`, но не из `Content-Length`
   ответа `200`. Если `head_size()` не смог узнать размер (нет HEAD/Range),
   полный файл скачивается, но `total` остаётся 0. Цикл повторяется до
   `attempts > 5000` и падает с `ExtractError`.
2. При возобновлении запрашивается диапазон `received … received + 64 КБ`
   (`RANGE_CHUNK`). Для файла больше ~320 МБ после обрыва это снова упирается
   в лимит 5000 попыток; скачивание идёт по 64 КБ на HTTP-запрос.

Проверка с mock-сервером, который отдаёт полный файл `200` с `Content-Length`,
но не поддерживает HEAD/Range:

```text
error ExtractError http://example.org/x.osm: слишком много попыток загрузки
calls 5000
```

**Исправление:**

- для ответа `200` с `Content-Length` устанавливать `total = body_expected`;
- при известном `total` использовать открытый Range `bytes=received-`
  (с откатом на закрытый диапазон при 416) либо увеличить `RANGE_CHUNK`;
- сбрасывать `stall` при реальном приросте `received`;
- добавить тесты «нет HEAD/Content-Range» и «возобновление большого файла».

### 2.2. DEM-кэш копируется целиком при каждом восстановлении

**Где:** `core/terrain_cache.py:24-39`, `_restore_item` — строки 371-397.

Все четыре DEM-файла (`merged_dem.tif`, `merged_dem_3857.tif`, `slope.tif`,
`hillshade_composite.tif`) включены в `COPY_ONLY_FILES`. Поэтому
`_restore_item()` всегда идёт в `shutil.copy2`, а не в `os.link`.
На крупном охвате это гигабайты чтения и записи на каждую подготовку,
хотя цель кэша — как раз не пересчитывать/не переписывать эти файлы.

Комментарий в `COPY_ONLY_FILES` объясняет причину (файлы могут быть
перезаписаны на месте), поэтому это осознанный компромисс, но его стоит
измерить и либо:

- разрешить hardlink после успешного `restore`, когда `build_dem()` точно
  не будет вызван;
- использовать reflink/copy_file_range, если ФС поддерживает;
- хотя бы логировать объём копирования в хронометраж.

### 2.3. Разобранный шаблон проекта занимает сотни мегабайт

**Где:** `core/poi_icons.py:80`, `core/poi_icons.py:434-448`.

`_template_root()` разбирает `automap.qgz` через
`ElementTree.fromstring` и сохраняет всё дерево в `_TEMPLATE_ROOTS`
на весь сеанс.

Замер на текущем шаблоне:

```text
XML: ~56 МБ
пик RSS при разборе: ~430 МБ
```

Для машины с 8 ГБ это заметная постоянная плата. Дерево нужно в основном
для POI-правил и нескольких слоёв из `overlay_*`; лучше:

- разбирать через `iterparse` и сохранять только нужные `maplayer`;
- или хранить компактные `PoiLayer`/`PoiLabelRule`, а не полное XML-дерево;
- `_template_variables` уже кэширует отдельно, полное дерево не обязательно.

## 3. Логические и надёжностные дефекты

### 3.1. Неверное значение поля `layer` в служебном слое POI

**Где:** `core/poi_icons.py:2076`.

```python
feature.SetField(indexes["layer"], str(point.rank))
```

Поле `layer` получает строку с рангом, а не имя слоя. Сейчас это поле,
похоже, нигде не читается, но данные заведомо неверные. Либо писать
`point.name`, либо убрать поле.

### 3.2. `_dissolve_fields` может растворить весь слой в один объект

**Где:** `core/pipeline.py:1037-1060`.

Если запрошенное поле отсутствует и в слое нет `@id`, функция возвращает `[]`.
`native:dissolve` с пустым `FIELD` сливает все объекты в один.
Нужно пропускать dissolve или использовать другой уникальный ключ.

### 3.3. `peak_filter`/`classify`: `ele_only` не пропускается

**Где:** `core/peak_placement.py:876-895`, `core/peak_filter.py:620+`.

Docstring `classify()` говорит: «проверяются только пики без названия и без
`ele`», но код пропускает только `category == "named"`. Безымянный пик с
тегом `ele` (`ele_only`) может быть удалён по другим критериям. Либо это
задумано (тогда исправить docstring), либо добавить пропуск `has_ele`.

### 3.4. Кэш тайлов DEM не проверяется на целостность

**Где:** `core/terrain.py:142` (`download_srtm`), `download_cog_dem`,
`core/sonny.py:486`.

- существующий `.hgt` считается готовым без проверки размера/структуры;
- COG-кэш проверяется только по `st_size > 0`;
- Sonny `.hgt` берётся по `exists()`.

После аварийного завершения обрезанный файл останется навсегда и будет
попадать в сборку. Стоит проверять ожидаемый размер (SRTM: 1201/3601 точек)
и/или открывать файл и проверять растр.

### 3.5. `geofabrik.fetch_index`: 304 при отсутствующем индексе

**Где:** `core/geofabrik.py:329`.

Если `index-v1.json` удалён, а `index-meta.json` с ETag остался, запрос
уходит с `If-None-Match`; сервер может вернуть `304`, после чего
`load_index(index_path)` падает на отсутствующем файле. Перед отправкой
условных заголовков нужно проверять `index_path.exists()`.

### 3.6. `BBox.as_csv(places=4)` как ключ кэшей

**Где:** `core/bbox.py:22`, `core/sources.py:83`, `core/slice_estimate.py:175`,
`core/terrain_cache.py:200,240,334`, `core/peak_filter.py:479`.

Кэши идентифицируются по координатам с точностью 4 знака (~11 м).
Два близких, но разных охвата получают один кэш. Если это осознанное
округление — задокументировать; иначе для ключей использовать полную точность.

### 3.7. `_mosaic_grid`: неверное сообщаемое разрешение

**Где:** `core/terrain.py:593-614`.

При переполнении бюджета возвращается `span_x / width`, хотя реальный шаг
по более длинной оси — `span_y / height`. Сообщение «Разрешение мозаики»
занижается для вытянутых по широте охватов.

### 3.8. `merge_if_available` — фактически мёртвый путь

**Где:** `core/geofabrik.py:825`, вызов в `core/sources.py:250`.

При `osmium_ready=True` используется `source_paths(prefer_separate=True)`,
а при `osmium_ready=False` `merge_if_available()` вызывает
`find_osmium()` без `temp_dir` и, как правило, тоже не находит бинарник.
Новый merged-файл в текущем потоке не создаётся; путь остаётся только
для старых кэшей. Либо убрать, либо использовать явно.

### 3.9. Отмена не прерывает часть GDAL-операций

**Где:** `core/terrain.py:1287` (`build_dem`), `1392` (`_generate_slope`),
`1426` (`_generate_hillshade`), `1163` (`_transform_raster`).

`gdal.Warp`/`DEMProcessing`/`WriteArray` не получают callback отмены.
Пользователь может ждать завершения долгой операции после «Отмены».
В `download_cog_dem` callback уже есть — стоит распространить на остальные
операции и проверять `cancel` в блоках `_transform_raster`.

### 3.10. Конкурентная запись служебных файлов Geofabrik

**Где:** `core/geofabrik.py:279` (`_write_meta`), `core/geofabrik.py:329`.

`_write_meta` использует фиксированное имя `*.part`, а `fetch_index` может
одновременно вызываться из потока подготовки и из `MapIndexWorker`.
Два процесса/потока могут писать один временный файл. У `extracts` для
этого уже есть уникальный `_temp_path()`; стоит применить тот же подход.

## 4. Производительность и память

- **`label_cache` считает полный digest слоя до проверки кэша.**
  `core/label_cache.py:25` → `terrain_cache.layer_digest()`
  (`core/terrain_cache.py:126`) обходит все объекты и экспортирует WKB.
  Для больших слоёв это может быть дороже сохранённого расчёта линии.
- **`poi_icons._collect_points()`** (`core/poi_icons.py:1332`) перебирает все
  объекты и для каждого проверяет все диапазоны/уровни через `QgsExpression`.
  На плотных областях это главный кандидат на минуты; полезно ограничить
  выборку bbox и кэшировать результаты правил.
- **Sonny-тайлы качаются последовательно** (`core/sonny.py:472`).
  При десятках тайлов это минуты сети; `download_srtm` уже умеет параллелить.
- **`overpass_batch.Selector.matches()`** компилирует regexp на каждом объекте
  (`re.search(value, actual)` в `core/overpass_batch.py:44`). Регулярки стоит
  компилировать при разборе селекторов.
- **`peak_filter.ProjectDem`** (`core/peak_filter.py:136`): при
  `prepare_shared() == False` окна читаются под общим `threading.Lock`,
  то есть проверка пиков фактически однопоточная для крупных DEM.
- **`peak_filter.SrtmTiles`** держит до 6 тайлов в памяти; один тайл
  3601×3601 float32 — около 52 МБ, итого до ~312 МБ.
- **`project.repair_project()`** при каждом открытии читает 56-МБ XML
  и проверяет датасорсы всех слоёв. На синтетическом проекте это ~0.8 с;
  на большом сетевом каталоге может быть заметно. Стоит кэшировать результат
  по mtime проекта.
