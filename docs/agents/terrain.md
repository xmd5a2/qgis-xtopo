# Источники рельефа, мозаика и кэш

Справочная часть `AGENTS.md`. Код — `core/dem_sources.py`, `core/terrain.py`,
`core/sonny.py`, `core/relief.py`, `core/terrain_cache.py`.

## Список источников

- **Единый список — `core/dem_sources.py`.** Ключи: `auto` (по умолчанию),
  `fabdem`, `srtm`, `cop30`, `nasadem`, `alos`, `3dep`, `sonny`, `manual` —
  в этом порядке они идут в списке интерфейса. Там же описание для интерфейса,
  покрытие, атрибуция и проверка доступности.
- `Config.terrain_source` хранит ключ; `resolved_terrain_source()` понимает
  старые `config.ini` без этого поля (`get_terrain_tiles=true` → `manual`, иначе
  `srtm` — это `LEGACY_DEFAULT_SOURCE`). В `config.ini` пишется явный ключ, у
  новых проектов — `auto`.
- **Ограничения покрытия**: у GLO-30 не опубликованы 25 тайлов (Армения,
  Азербайджан, СЗ Иран, Туркменистан), NASADEM только −56…61°, 3DEP — США,
  Канада и Мексика, FABDEM — 60° ю.ш. – 80° с.ш. Не предлагать эти наборы там,
  где данных нет.
- Для `cop30`/`nasadem`/`alos`/`3dep` доступность и список тайлов берутся из
  STAC Planetary Computer; для SRTM — по широтному покрытию −56…60°, для
  Sonny — по локальному каталогу тайлов, ручной каталог доступен всегда.
  **FABDEM — без каталога STAC** (`direct_tiles`): адрес тайла строится по
  координатам (`fabdem_tile_url`, блок 10°×10° в бакете Hugging Face), а
  наличие файла проверяется HEAD-запросом (`dem_sources._tile_status`):
  тайлы опубликованы не для всей суши. Сетевые ошибки HEAD не помечают сеть
  недоступной для остальных наборов — запросы идут отдельным `urlopen`.
- **Одна вертикальная система на проект**: SRTM/NASADEM — EGM96,
  Copernicus/ALOS/FABDEM — EGM2008, 3DEP — NAVD88. Смешивать нельзя. ALOS —
  DSM, FABDEM — DTM (Copernicus без леса и построек), 3DEP — DTM. Разные
  системы в мозаике показываются предупреждением `mixed_datum_warning`: на
  границах тайлов возможны ступеньки. Для обычных наборов правило прежнее —
  один набор на проект.
- **FABDEM — только некоммерческое использование** (CC BY-NC-SA 4.0).
  В авторежиме он идёт фоном после ALOS, поэтому данные набора попадают и в
  проекты, собранные «Автоматически»; атрибуция обязательна и пишется в
  `dem_attribution`, как у Copernicus и ALOS.
  По суше в поясе 60° ю.ш. – 80° с.ш. у FABDEM есть всё, кроме тех же тайлов,
  которых нет у GLO-30 (Армения, Азербайджан, СЗ Иран): набор построен из
  GLO-30. За полярными широтами (Антарктида, север Гренландии, Канады и
  Шпицбергена) данных нет — там остаются другие наборы.

## Проверка доступности

- **Проверяется сразу после изменения охвата, в фоне и до открытия вкладки
  «Рельеф»** (`DemAvailabilityWorker` в `gui/dockwidget.py`). Наборы без данных
  для охвата отключаются в списке, выбранный недоступный источник заменяется
  подходящим. Проверка идёт параллельно по всем наборам
  (`ThreadPoolExecutor` по числу источников), результат кэшируется в
  `_CHECK_CACHE` (успех 30 минут, ошибка 2 минуты); кнопка ⟳ у списка
  источников вызывает `check_availability(force=True)`.
- **Сбой сети не отключает набор**: `Availability(checked=False)` с сообщением
  «не удалось проверить». Для Copernicus при недоступном STAC покрытие
  проверяется прямыми HEAD-запросами к открытому зеркалу AWS
  (`_cop30_file_availability`). У FABDEM каталога STAC нет, поэтому покрытие
  всегда проверяется HEAD-запросами по тайлам охвата (`tile_statuses`,
  8 потоков): для охвата в полстраны это десятки секунд, зато результат
  кэшируется на 30 минут. Если хост не ответил ни по одному тайлу — это
  «не удалось проверить», а не «нет данных». Число HEAD-проверок ограничено
  `DIRECT_HEAD_LIMIT`: при большем охвате честнее сообщить «слишком много
  тайлов для проверки», чем считать непроверенные тайлы доступными.
- **Пустой план ещё не значит «нет суши».** `download_auto_dem` строит
  план по суше (`required_tiles` из Natural Earth и берега/островов OSM).
  Если суша есть, но ни один источник не проверен из-за сети, бросается
  `TerrainUnavailable`: в журнал идёт `WARNING` с текстом последней сетевой
  ошибки. Совет проверить настройки прокси добавляется только при
  включённом прокси, иначе просят проверить доступность сети. Сообщение
  «в охвате нет суши» остаётся только для действительно пустого
  `required_tiles`. Такой сбой не прерывает сборку: проект готовится без
  рельефа (`prepare_terrain_raster` возвращает `None`).
- **STAC отвечает нестабильно**: системный DNS иногда возвращает адрес Azure
  Front Door с закрытым портом 443. `_MultiAddressHTTPSConnection` перебирает
  все адреса из ответа DNS, а если они не открылись — берёт A-записи у
  публичных резолверов (UDP DNS, затем DoH) и пробует их; рабочий адрес
  запоминается на сеанс.
- Строки доступности в панели короткие (`Availability.message`), полные
  формулировки — в `Availability.detail` и подсказке. Подпись в панели —
  `WrappedLabel`: высота считается по фактической ширине, иначе в узкой
  панели обрезается последняя строка с числом тайлов.

## Режим «Автоматически»

- `AUTO_SOURCE` — не набор, а подбор по тайлам 1°×1°. Приоритет
  `AUTO_PRIORITY`: `3dep` → `sonny` → `fabdem` (фон) → `cop30` → `srtm`
  (`dem_sources.auto_plan`). В горных регионах встаёт `alos`
  (`MOUNTAIN_PRIORITY`: `3dep` → `sonny` → `alos` → `fabdem` → `cop30` →
  `srtm`): 3DEP и Sonny остаются выше него, ALOS — выше FABDEM, потому что
  резче на склонах. Горность
  определяется `core/relief.py` по встроенной сетке
  `resources/data/relief_grid.npz` (1°, минимум и максимум высоты из ETOPO5,
  ~194 КБ; ~0.02 мс на охват, без сети). Охват горный, если перепад высот
  ≥ 800 м хотя бы у 25 % тайлов суши; так Турция, Непал и Кавказ получают
  ALOS. Sonny покрывает Европу (`europe-1s`), поэтому Дания и Польша
  остаются на Sonny, а равнины вне его покрытия (например, степь Казахстана) —
  на FABDEM, и только где его тайлов нет — на Copernicus. Сетка
  пересобирается `tools/build_relief_grid.py`.
  Принудительного автовыбора 3DEP больше нет: прежняя логика
  `preferred_source` осталась только для предупреждения `source_warning`,
  когда пользователь выбрал набор вручную.
- **3DEP выбирается автоматически**, если покрывает всю сушу охвата
  (`dem_sources.preferred_source`). Суша определяется по Natural Earth из
  ресурсов QGIS (`<QGIS>/resources/data/world_map.gpkg`, слой `countries`),
  а не по покрытию ALOS/Copernicus: те публикуют и океанские тайлы с нулевыми
  высотами. Если Natural Earth недоступен, используется покрытие
  ALOS/Copernicus, а при его отсутствии требуется покрытие всех тайлов. Ручной
  выбор другого источника для такого охвата даёт предупреждение
  (`source_warning`), «Свой каталог» не перетирается.

## Сборка мозаики

- `terrain.download_auto_dem`: сначала каждый набор приводится к общей сетке
  отдельным слоем, затем `gdal.Warp` по списку слоёв, где **поздний источник
  перекрывает ранний, а его nodata не затирает ранние данные** (проверено).
  Разрешение мозаики — самый подробный шаг из входящих наборов, который
  влезает в `MAX_DEM_PIXELS`; иначе берётся более грубый шаг.
  `download_sonny_dem` — тот же код с приоритетом `sonny` → `cop30` → `srtm`.
- **Медленный набор заменяется следующим по приоритету** (`terrain._SpeedGuard`,
  `SLOW_DOWNLOAD_RATE = 100 КБ/с`, `SLOW_DOWNLOAD_WINDOW = 60 с`). Скорость
  оценивается окнами по минуте: тайлы, приведённые к общей сетке, пишутся в
  файлы слоя по мере чтения (`terrain._layer_bytes`), у Sonny байты считает
  читающий цикл (`sonny._http_bytes(..., on_chunk=guard.add)`). GDAL точного
  счётчика скачанных байт не отдаёт, а общий сетевой счётчик процесса смешал
  бы рельеф с загрузкой OSM, идущей параллельно. При срабатывании
  `gdal.Warp` прерывается через callback, `SlowDownload` не повторяется как
  сетевой сбой, а тайлы уходят наборам ниже по списку `auto_priority` (с
  учётом горности), для новых ячеек собирается отдельный слой; в журнал идёт
  `WARNING: <набор> отдаёт слишком медленно (<скорость>); тайлы берут: …`.
  Переключение из-за скорости разрешено только один раз за сборку
  (`download_auto_dem.slow_switched`): после него сторож не создаётся, и
  следующие наборы докачиваются без ограничения, чтобы не передавать тайлы
  по кругу. Ручной выбор набора (`download_cog_dem`) не заменяется:
  пользователь выбрал его явно. Порог и окно можно проверить тестами
  `_SpeedGuard` без сети.
- **Ручной GLO-30 с нехваткой тайлов**: `terrain._download_cop30` проверяет
  покрытие (`auto_coverage`); при полном покрытии идёт обычный
  `download_cog_dem` с кэшем окон, иначе тайлы раскладываются `cop30` →
  `srtm` и собирается мозаика. Сообщение о замене пишется в рантаймовое
  `config.terrain_fallback` (в `config.ini` не сохраняется), панель показывает
  его в `dem_warning`, журнал — отдельной строкой.
- **Растровые наборы читаются по HTTP Range через `/vsicurl`** и сразу
  переводятся в локальное окно EPSG:4326 (`terrain.py: download_cog_dem`).
  Список ссылок для наборов без каталога STAC собирает
  `terrain._direct_sources`: тайлы охвата проверяются HEAD-запросами, а
  адреса строятся по координатам (`dem_sources.fabdem_tile_url`).
  Запас вокруг охвата `COG_PADDING = 0.002°`: тайлы Copernicus сдвинуты
  относительно целых градусов, без запаса у края остаётся полоса nodata. Окно
  ограничено `MAX_DEM_PIXELS` (120 млн пикселей); для больших охватов
  разрешение снижается, об этом пишется в журнал.
- **STAC отдаёт тайлы южнее и западнее запроса**: например, на окно 3°×2° —
  20 тайлов вместо 6. Объекты вне окна отбрасываются сразу
  (`terrain._item_overlaps`), иначе их ссылки подписываются и читаются при
  сборке мозаики впустую.
- **Сетевой сбой при сборке растра не валит рельеф.** `terrain._warp_with_retry`
  повторяет `gdal.Warp` до трёх раз (паузы 5 и 10 с), а `download_cog_dem`
  перед повтором заново подписывает ссылки Planetary Computer: подпись живёт
  час, и сборка большого окна может её пережить. Дополнительно GDAL повторяет
  HTTP-запросы (`GDAL_HTTP_MAX_RETRY=4`). В режиме «Автоматически» сбой набора
  после повторов не прерывает подготовку: его тайлы добирает SRTM, в журнал
  идёт `WARNING: не удалось собрать <набор>: <причина>`. В тексте ошибки
  остаётся сообщение GDAL, а не только название набора.
- **Удалённые COG перед мозаикой скачиваются параллельно**
  (`terrain._fetch_cog_windows`, `COG_PREFETCH_WORKERS = 6`): каждый тайл
  отдельным `gdal.Warp` приводится к общей сетке с `dstNodata=-32768`, затем
  финальный warp собирает локальные файлы. Область вне тайла получает nodata,
  поэтому источники не перекрывают друг друга нулями; результат бит-в-бит
  совпадает с прямым warp'ом (проверено на ALOS, 6 тайлов). Число потоков
  здесь не зависит от ядер: это сетевые загрузки. Тайлы грубее
  `MAX_COG_PREFETCH_PIXELS` (3DEP 10 м) остаются на прямом `/vsicurl`, иначе
  предзагрузка читает сотни мегапикселей.
- **Открытое зеркало Copernicus в AWS неполное**: у части тайлов есть только
  AUXFILES и XML. Адрес AWS используется, только если файл реально есть
  (HEAD), иначе ссылка из STAC подписывается (`sign_pc`). Если каталог STAC
  не ответил, покрытие Copernicus считается полным, а неоткрывшиеся тайлы
  пропускаются при сборке слоя.
- **Атрибуция источников пишется в переменную проекта `dem_attribution`**;
  подпись макета атласа (рядом с OSM) выводит её через
  `[%if(@dem_attribution ...)%]`. `rewrite_project_archive` получает
  `dem_attribution` из выбранного источника. Рамка подписи — 210 мм: это
  предел переноса длинной строки, но видимый прямоугольник подгоняется по
  тексту (`ProjectPanel._fit_copyright_label` вызывает `adjustSizeToText()` при
  открытии проекта и перед экспортом). Иначе белая полоса тянется на все
  210 мм.
- Верхняя граница охвата не включает тайл, начинающийся ровно на ней:
  `tiles_for_bbox` использует `ceil(max) - 1`.
- **Журнал называет скачиваемый файл каждого тайла всех источников** —
  «Загрузка тайла рельефа: N46E006.hgt.gz (SRTM v3 (skadi), 30 м)»,
  «…Copernicus_DSM_COG_10_N46_00_E009_00_DEM.tif (Copernicus GLO-30)».
  Иначе параллельные загрузки неотличимы. SRTM — в `download_srtm`
  (terrain.py), растровые наборы — по имени URL в `_cog_sources`, Sonny — в
  `sonny.download_tile`.
- Оценка времени в панели (`dockwidget.py: _estimate_seconds`) считается от
  доли области в выгрузке (`pbf_fast.py: extended_ratio`), а не от общего
  числа объектов; прежняя формула завышала в 3–8 раз.
- **Площадь рельефа в оценке — это суша, а не вся рамка.** DEM качается
  только по тайлам с землёй, поэтому `dem_sources.land_area_km2` суммирует
  полигоны Natural Earth, обрезанные рамкой (не тайлы 1°×1°: на архипелаге
  целый квадрат океана считался бы сушей). Изолинии же строятся по всему
  растру до маски воды, поэтому `performance.estimate_terrain_seconds`
  принимает `frame_area_km2` отдельно. Без этого оценка на Таити
  показывала 53 мин вместо реальных 10: рамка 250 тыс. км², суши — 1,5 тыс.
  км².
- **Место на диске проверяется заранее** (`core/disk_space.py`): уклон,
  отмывка и мозаика лежат в разрешении DEM, все производные растры рядом.
  Перед расчётом рельефа `generate_hillshade_slope` оценивает пиковый
  объём (`disk_space.relief_estimate`) и, если места не хватает, пишет в
  журнал `WARNING: Недостаточно места для рельефа: нужно ≈X, свободно Y`.
  Перед каждой крупной записью (`_transform_raster`, укрупнение для
  сглаживания контуров, уклон, оттенок) `disk_space.require_space`
  бросает `InsufficientSpace` с понятным текстом, а ошибка GDAL
  «TIFFAppendToStrip:Write error» на заполненном томе переводится в то
  же сообщение (`terrain._write_error`). Незаконченный
  растр удаляется, чтобы не занимать место. Панель показывает свободное
  место в строке «Свободно на диске» (`dockwidget._update_disk_info`).
  Оценка завышена против замера: на DEM 16346×6674 (109 млн пикселей)
  после отказа от укрупнения она составляет около 2,4 ГБ. Проверка перед
  отдельным файлом считается по верхней границе
  (`FILE_FLOAT_PIXEL = 4`, `FILE_BYTE_PIXEL = 1` байта на пиксель): LZW
  жмёт высоты слабо, поэтому меньшая оценка пропустила бы нехватку места.

## Sonny

- **Sonny DTM — один источник из нескольких наборов** (`core/sonny.py`):
  `at-05s`, `ch-05s` (0,5″), `europe-1s`. Набор 3″ (около 90 м) не
  используется: где нет 1″, фоном идёт Copernicus 30 м. Список тайлов берётся
  из Google Drive (`embeddedfolderview`, коллективным папкам нужен
  `resourcekey`), кэшируется на неделю в `~/.cache/qgis-xtopo/sonny` и
  обновляется в фоновом потоке при старте панели. Скачанные тайлы лежат в
  `<проекты>/qgisxtopo-cache/sonny/tiles`.
- Файлы Sonny — zip с одним `.hgt` без заголовка (big-endian int16,
  3601/7201/1201 точек). Драйвер SRTMHGT читает 1201 и 3601, для 7201 нужна
  VRT-обёртка `sonny.hgt_vrt`. Вода и пустоты заполнены нулями, а не
  `-32768`, поэтому нули считаются данными.

## Кэш

- `terrain_cache.py` переиспользует DEM/изолинии, пока совпадают версия
  расчёта (`DEM_VERSION`, `HILLSHADE_STYLE_VERSION`, `ISOLINES_VERSION`),
  параметры (шаг, сглаживание, ресемплинг) и исходные данные. Версия плагина
  в ключ не входит: обновление интерфейса не должно пересчитывать DEM.
  Меняя формат результатов, добавляйте новые файлы в `DEM_FILES`/
  `ISOLINES_FILES` и поднимайте нужную версию, иначе старый кэш отдаст
  устаревшее.  Записей DEM хранится одна (`KEEP_ENTRIES = 1`): старые
  версии рельефа только занимают место.
- **Кэш рельефа проверяется до скачивания тайлов** — по подсказке
  `terrain_cache.dem_hint` (версия расчёта, область, источник, параметры; для
  ручного каталога и локальных тайлов — отпечаток файлов). Полный ключ требует
  хеша содержимого тайлов, а подсказка — нет, поэтому повторная подготовка не
  ходит в сеть и не собирает мозаику. Подсказки лежат в
  `terrain_result_cache_dir/dem-hints` (хранится `KEEP_HINTS` штук);
  `store_dem_hint` вызывается после `store_dem`. Если наборы/сообщение о
  замене тайлов должны переживать восстановление из кэша — добавляйте их в
  данные подсказки.
- **Ключи рельефа и изолиний берут содержимое слоёв воды, а не mtime.**
  `relief_signature` и `isolines_signature` используют
  `terrain_cache._layer_digest`: файлы слоёв перезаписываются при каждой
  подготовке, и отпечаток по времени изменения не давал кэшу попадать даже
  при тех же данных.  В `ISOLINES_FILES` входят и общие
  `isolines_full*`/`isolines_full_overview*`: без них восстановление из кэша
  теряло слои, которые проект ожидает найти.  Меняя набор сохраняемых
  файлов, поднимайте `ISOLINES_VERSION`.
- **Восстановление растров из кэша не копирует лишнего**: файлы, которые уже
  лежат на месте с тем же размером и mtime, пропускаются, а остальные
  связываются с кэшем жёсткой ссылкой. Копия гигабайтных растров стоила
  больше 20 секунд на каждый прогон. Ссылка безопасна: `build_dem` и
  `generate_hillshade_slope` удаляют прежний файл перед записью, поэтому
  записать в кэш на месте нельзя.
- **Копии DEM в EPSG:3857 нет.** `raster_value()` принимает координаты в
  системе координат слоя, а все слои OSM лежат в EPSG:4326, поэтому
  отдельный растр не использовался. `build_dem` удаляет
  `merged_dem_3857.tif` и его `.sha256` из проектов прежних версий.
- **Запись в кэш тоже ссылкой**: `store_dem`/`store_isolines` связывают
  файлы проекта с файлами кэша. Места на диске хватает вдвое: кэш и
  проект делят одни и те же данные.
- **Отмывка — как `gdaldem hillshade` по умолчанию**: солнце 315°/45°, без
  вертикального преувеличения, плюс 10 % подсветки теней
  (`terrain.py: generate_hillshade_slope`). Многонаправленная отмывка с
  `altitude=70`, `zFactor=2` и примешиванием уклона давала почти белое полотно.
  Меняя параметры, поднимайте `HILLSHADE_STYLE_VERSION` в
  `terrain_cache.py`, иначе кэш вернёт старую картинку. Шкала var1 в шаблоне
  привязана к «плоскому» значению 190: после изменения высоты солнца или
  подсветки теней её нужно сдвинуть.
- **Уклон и отмывка считаются в два потока** (`generate_hillshade_slope`):
  ветки читают только `merged_dem.tif` и пишут каждая в свои файлы, поэтому
  идут параллельно.
- **Растры рельефа пишутся без `NUM_THREADS`** (`_relief_creation_options`):
  при многопоточном сжатии GDAL 3.8 раскладывает полосы крупного
  файла по разным местам — размер выходит в разы больше суммы полос
  (42 ГБ вместо 4 ГБ на DEM 16346×6674), часть полос пустая, а чтение
  падает с `TIFFReadEncodedStrip() failed`. Раскладка идёт блоками по
  2048 полос — размеру блока `_transform_raster`. Гонка в писателе
  проявляется не каждый раз, поэтому пишем однопоточно: тот же
  конвейер без `NUM_THREADS` даёт целые файлы, размер которых совпадает
  с суммой полос.
- **Пиксельная обработка растров идёт блоками** (`_transform_raster`,
  блок 2048×2048): применение порога к уклону и подсветка теней не читают
  весь растр в numpy. На области 300 км уклон и его итоговый растр —
  это сотни мегабайт на float32, и старый вариант падал по памяти. Кэш GDAL
  тоже ограничен бюджетом (`core/memory.py: gdal_cache_bytes`), а не
  значением по умолчанию. Число потоков изолиний урезается тем же бюджетом
  (`CONTOUR_WORKER_BYTES`, 768 МБ на тайл): на 8 ГБ 12 тайлов одновременно
  занимали больше 6 ГБ.
- **Уклон и отмывка — в разрешении DEM** (`_generate_slope`,
  `_generate_hillshade`): искусственного укрупнения больше нет. Раньше DEM
  удваивался, чтобы сгладить отмывку, но QGIS передискретизирует растры
  бикубом при увеличении (`core/project.py: patch_raster_resampling`),
  поэтому запас пикселей только раздувал файлы и подготовку. Отдельного
  файла `merged_dem_upscaled.tif` больше нет: шаблон и выражения склонов
  читают `merged_dem.tif`. Уклон пишется в `raster/slope.tif` байтом
  (1°, nodata 255): шкалы уклонов дискретные с шагом 5° и 2°, поэтому
  квантование не видно, а файл вчетверо легче Float32. Старое имя
  `slope_upscaled.tif` осталось только для уже подготовленных проектов
  (`core/slope_style.py: LEGACY_SLOPE_FILE`).
- **Единицы изолиний — часть подготовки, а не отображения.**
  `Config.isolines_units` (`m`/`ft`, по умолчанию `m`) вкладки «Рельеф»
  входит в `isolines_signature`: метры и футы не переиспользуют кэш. DEM
  всегда в метрах, поэтому шаг в футах переводится в метры
  (`_contour_step_meters`), контуры ложатся на круглые значения футов, а
  поле `ELEV` пересчитывается обратно в футы (`_contour_tile` и
  `_contour_untiled`). Кратности в футах — 20, 40, 100, 200, 500, 1000
  (по умолчанию 40), как в OsmAnd-tools V4. Единицы записываются в проект
  переменной `map_units_data`; список на вкладке «Проект» меняет только
  отображение (`map_units`), изолинии не пересчитывает и при расхождении
  предупреждает.
- **Изолинии готовятся за один проход по DEM**: подробный набор без
  упрощения (`isolines_regular/glacier.sqlite`, до 1:50000) и обзорный
  с допуском `min(10 м, шаг изолиний в метрах)` (`*_overview.sqlite`,
  с 1:50001). Упрощённая копия пишется в потоках тайлов из тех же
  контуров. Вода полностью вычитается в подробном наборе, а обзорный
  проверяет только линии, обрезанные в подробном (отклонение
  упрощения — не больше 10 м). Ледники режутся в обоих наборах.
  Версия кэша — `ISOLINES_VERSION` (на момент проверки 11); в
  `ISOLINES_FILES` входят все четыре файла.
- **Тайлы изолиний считаются процессами** (`core/terrain_worker.py`).
  Контуры, вычитание воды и разрезание по ледникам держат GIL, поэтому
  потоки на этой стадии не ускоряют расчёт: на охвате Гренландии
  (-45.92,59.65,-42.74,60.60, DEM 11460×3424) один поток дал 24 с на
  контуры и 105 с на всю стадию, девять потоков — 48 и 132 с. Работа идёт
  в два этапа: сначала тайл целиком считается процессом (контуры, вода,
  запись промежуточного SQLite, около 14 с), затем разрезание по
  ледникам раздаётся частями по `ISOLINE_CHUNK` (4000) строк
  `ogc_fid` — фильтр ставится прямо на файл тайла, копии не создаются.
  Дробление нужно из-за перекоса: один тяжёлый тайл занимал около 23 с,
  а его части идут параллельно. Стоимость разрезания определяется числом
  полигонов-кандидатов, а не вершин: у упрощённого обзорного слоя
  пересечений столько же, и он стоит почти как детальный. Родитель
  склеивает результаты в порядке
  номеров тайлов и частей, поэтому ID и `SRC` совпадают с
  однопроцессным путём, а данные — побайтово (проверено
  `compare_projects.py`). Склейка тоже идёт процессами: полные слои
  переводятся напрямую в SpatiaLite (`FORMAT=SPATIALITE`,
  `COMPRESS_GEOM`), пары `regular`/`glacier` собираются отдельно.
  Обязателен `-dsco SPATIALITE=YES`: без него `-lco SPATIALITE=YES`
  молча игнорируется, и вместо `"GEOMETRY" LINESTRING` получается
  неspatial BLOB `geometry`. На этом охвате стадия занимает около 35 с
  (было 55 с).
  Скрытая зависимость от `QgsApplication` в дочернем процессе не нужна:
  `terrain_worker.py` импортирует только GDAL/OGR и пакет плагина.
  Если подходящий Python не найден (или задан
  `QGIS_XTOPO_NO_ISOLINE_PROCESSES=1`), `generate_isolines` откатывается
  на прежний путь с shapefile и `_finish_isoline_set`. Число процессов
  ограничено `ISOLINE_PROCESS_BYTES` (1,5 ГБ) и 3/4 ядер; в каждом
  процессе `GDAL_CACHEMAX=256` МБ, а не общий бюджет.
- **Изолинии идут параллельно значкам POI.** После пересечений полигонов
  `prepare_terrain_isolines` запускается в потоке `xtopo-isolines`; POI
  читает другие слои, а упаковка, переписывающая воду и ледники, стартует
  только после join. Холодная сборка экономит около 0,4 с, данные
  совпадают с последовательным вариантом.
- **Вода вычитается из готовых изолиний** (`_subtract_water_from_layer`):
  раньше вода растеризовалась в DEM как nodata с `ALL_TOUCHED=TRUE`, из-за
  чего маска расширялась на пиксель (около 30 м) и линии обрывались, не
  доходя до берега. Теперь контуры считаются по всему DEM, а полигоны воды
  вычитаются GEOS: концы ложатся точно на берег, форма линии вне воды не
  меняется. Обрезка идёт до деления на ледниковые и обычные, поэтому обе
  группы не заходят на воду.
- **Пересечение с водой проверяется подготовленной GEOS-геометрией.**
  Море в архипелаге — один мультиполигон с тысячами дырок-островов, и
  `Intersects` с ним для каждой горизонтали заново обходил все кольца:
  на юго-западной Финляндии 46–66 с. `CreatePreparedGeometry` строит
  индекс рёбер один раз и снижает проверку до 0,5 с; `Difference`
  по-прежнему считается по исходному полигону, поэтому WKB всех линий
  совпадает. Если GDAL собран без GEOS, остаётся обычная проверка.
- **«Сглаживать контуры»** — единственное место, где DEM ещё укрупняется
  вдвое: `_smoothed_isolines_dem` делает временный
  `tmp/isolines_dem_x2.tif`, контуры считаются по нему и файл удаляется.
  Уклон и отмывка этот растр не используют.
- Кэш окон COG — `<проекты>/qgisxtopo-cache/srtm/cog/<источник>`; ключ включает
  охват. Меняя запас, формат окна или источник данных, поднимайте версию
  `v1` в `terrain.py: _cached_cog`, иначе старый кэш отдаст устаревшее.
  Перед загрузкой `terrain_input_dir` очищается, иначе в сборку попадут
  тайлы другого набора.
