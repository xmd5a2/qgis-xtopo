# Поддержка тега `layer` в qgis-xtopo

Дата: 2026-11-28.
Статус: исследование, код не менялся.

Задача: реализовать семантику OSM `layer` для основных объектов так, чтобы
она была глобальной, как в OsmAnd default style: например, `highway layer=-1`
должен оказаться ниже `railway layer=0`, а не просто ниже соседней копии
дорог. Учитывать скорость подготовки данных и скорость рендеринга.

## 1. Главный вывод

В QGIS нет per-feature z-index. Порядок отрисовки задаётся только положением
QGIS-слоя в дереве проекта. Поэтому глобальный `layer` нельзя реализовать
одним выражением в стиле или одним полем `z_order`: нужны отдельные
QGIS-слои-полосы.

Рекомендуемая схема:

1. Три глобальные полосы: `layer < 0`, `layer = 0`, `layer > 0`.
2. Один SQLite-файл на объектный слой, без физического размножения файлов.
3. Копии-полосы читают тот же файл через `|subset=...`.
4. Положительные копии ставятся в существующую группу мостов, отрицательные —
   в существующую группу туннелей.
5. `orderBy` в QGIS для больших слоёв не использовать: на SQLite он
   вычитывает и сортирует все объекты в памяти каждый кадр.

Ожидаемая цена: почти ноль дополнительного времени подготовки, примерно
+0,3–0,8 с на кадр при 10–15 небольших копиях и +4–7 МБ к шаблону проекта.

## 2. Как `layer` работает в OsmAnd default

В OsmAnd у объекта есть глобальный `order`. Категория задаёт базовый
`order`, а `layer` сдвигает его на категорийно-зависимую величину:

| Объект | База | `layer=-2` | `layer=-1` | `layer=+1` | `layer=+2` | `layer=+3` |
|---|---:|---:|---:|---:|---:|---:|
| motorway | 84 | 41 | 62 | 107 | 137 | 165 |
| railway | 86 | 19 | 44 | 108 | 138 | 167 |
| waterway | 9 | — | скрыт | 112 | 141 | 168 |
| building | 10 | — | 9 | 11 | 12 | 13 |
| barrier | 63 | 19 | 20 | — | — | — |

Отсюда два важных вывода:

- `layer` действительно глобальный для линейных объектов: `highway layer=-1`
  (order 45–62) уходит ниже `railway layer=0` (86).
- Это не тотальная сортировка по числу: у зданий `layer=+3` даёт order 13 и
  всё равно остаётся ниже дорог. OsmAnd использует «базовый порядок
  категории + смещение по layer», а не `z = layer`.

Для xtopo нужна таблица эффективных полос по категориям, а не одна числовая
шкала.

Источник: `rendering_styles/default.render.xml` из
`osmandapp/OsmAnd-resources`, ветка master на 2026-11-28. Дороги:
`<case tag="highway" ... order="84">` и вложенные `apply_if layer=...`;
rails — `order="86"`; waterway — `order="9"`; building — `order="10"`.

## 3. Текущее состояние qgis-xtopo

### 3.1. Что уже сделано

`core/pipeline.py: _split_layer` делит `highway_main` на три файла:

- `highway_main.sqlite` — `layer = 0` или NULL;
- `highway_main_layer_1.sqlite` — `layer > 0`;
- `highway_main_layer_-1.sqlite` — `layer < 0`.

В шаблоне копии стоят рядом с базовым слоем внутри группы `highway main`, а не
в глобальных полосах. Остальные объекты `layer` не используют: railway,
waterway, barrier, building, track, path.

### 3.2. Текущий порядок слоёв

Индексы получены через `QgsProject.layerTreeRoot().layerOrder()` на текущем
`automap.qgz`. Меньший индекс = выше в легенде, то есть объект рисуется позже
и оказывается сверху.

| Индекс | Слой |
|---:|---|
| 122 | `railway all` |
| 126 | `highway main layer >=1` |
| 128 | `highway main` |
| 130 | `highway main layer <=-1` |
| 138 | `barrier way` |
| 149 | `building` |
| 180 | `water` |
| 187 | `stream` |
| 196–200 | `rail tunnel`, `highway main tunnel`, `river/stream/canal tunnel` |
| 217 | `wood` |

Нарушения глобальной семантики:

- `highway layer=+1` (126) рисуется ниже `railway layer=0` (122).
- `railway layer=-1` остаётся в `railway all` (122), то есть выше
  `highway layer=0` (128).
- `highway layer=-1` (130) ниже `railway layer=0` (122), то есть пример из
  задачи сейчас выполняется случайно, но эта же дорога всё ещё выше зданий
  (149) и воды (180).
- `water/stream layer=-1` не отделены от поверхностных; `waterway layer=+1`
  (акведук) не поднимается выше дорог.
- `barrier layer=-1` (внутри 138) остаётся выше воды (180), хотя должен
  уходить ниже.
- У `building layer=+1` порядок внутри слоя произвольный.

| `stream` | 15 049 | 785 | 7 |
| `stream_intermittent` | 11 838 | 976 | 1 |

Вывод: почти всё — это `-1`, `0`, `+1`. Значения `±2`, `±3` редки, но
встречаются у дорог, зданий и мостов.

### 3.4. Скрытые проблемы, которые нужно решить вместе с `layer`

- `layer` не входит в ключи упаковки `railway_all`, `stream`,
  `stream_intermittent`, `power_minor_line`, `building`. После `pack_*`
  объекты с разным `layer` могут слиться в один мультиобъект, и слой получит
  значение первого объекта.
- `highway_main_bridge` растворяется через `dissolve("highway")` — `layer`
  теряется/смешивается.
- `PATH` и `TRACK` не сохраняют поле `layer`: его нет в пресетах
  `core/field_subset.py`.
- `highway main overview` и `[blocking] highway main overview` читают
  `highway_main.sqlite` через `subset` только по классу дороги. Если убрать
  физическое деление, туда попадут и `layer>0`, и `layer<0`; подписи и
  отрисовка задвоятся.
- `_is_empty_datasource` в `core/project.py` не учитывает `subset=`.
  Копия-полоса, у которой в данных нет объектов, никогда не будет удалена из
  проекта.

## 4. Варианты реализации

| Вариант | Подготовка | Рендер | Глобальность | Сложность |
|---|---|---|---|---|
| Физическое деление всех слоёв (`split_layer` для railway/water/building/barrier) | +0,1 с на дороги, ~+3 с на 1 млн зданий | базовый слой читает только `layer=0`, копии крошечные; быстро | да | средняя: деление до упаковки, копии не пакуются |
| Один файл + `subset`-копии | ~0 | фильтр `subset` почти бесплатен | да | низкая/средняя: нужна чистка пустых слоёв с учётом subset |
| `orderBy` в одном слое | 0 | на SQLite сортирует все объекты в памяти каждый кадр | нет: только внутри одного QGIS-слоя | низкая, но не решает задачу |
| Один «мега-слой» со всеми линиями | 0 | непредсказуемо | да | очень высокая: ломает стили, подписи, блокировщики, видимость |
| Динамические копии при сборке проекта | 0 | как subset | да | высокая: клонирование maplayer, ID, дерево |

### 4.1. Почему не `orderBy`

`QgsFeatureRequest.OrderBy` умеет сортировать объекты внутри одного слоя.
Но:

- оптимизированный `ORDER BY` в OGR-провайдере включается только для
  GeoPackage (`src/core/providers/ogr/qgsogrfeatureiterator.cpp:
  prepareOrderBy`);
- для SQLite QGIS делает fallback: вычитывает все объекты в память и
  сортирует через `QgsExpressionSorter` (`src/core/qgsfeatureiterator.cpp:
  setupOrderBy`);
- это повторяется каждый кадр и масштабируется по числу видимых объектов.

Замеры только чтения объектов в пределах кадра (QGIS 3.44.7, Люксембург):

| Слой | Обычное чтение | `orderBy` по `layer` |
|---|---:|---:|
| highway, 15 885 объектов | 0,31–0,35 с | 0,40–0,56 с |
| building, 22 986 объектов | 0,65–0,66 с | 0,92–1,26 с |

Для маленьких копий (`layer>0` — сотни объектов) `orderBy` допустим. Для
базового слоя зданий или дорог — нет.

### 4.2. Почему не дублировать базовый файл

Физическое деление не так дорого, как кажется, если не писать базовый файл
трижды:

- обычное сохранение `highway_main` — 0,55 с, деление на три файла — 0,67 с,
  то есть лишние ~0,12 с;
- обычное сохранение `building` (1 млн объектов, выбранные поля) — 63,3 с и
  153 МБ; дополнительные `layer>0` и `layer<0` — 1,7 с и 1,3 с, то есть
  примерно +3 с, а не +63 с.

То есть физическое деление по времени приемлемо. Основная сложность —
порядок с `pack_roads`/`pack_all`: делить нужно до упаковки, иначе копии
останутся неупакованными, либо упаковку придётся учить работать с копиями.
Для нового кода проще один файл + `subset`.

## 5. Рекомендуемая схема

### 5.1. Глобальные полосы

Минимальная модель, которая выполняет глобальную семантику:

| Объект | `layer < 0` | `layer = 0` | `layer > 0` |
|---|---|---|---|
| highway / track / path | подземная полоса | поверхность | надземная полоса |
| railway | подземная | поверхность | надземная |
| river / canal / stream | подземная | поверхность | надземная |
| barrier | подземная | поверхность | надземная |
| building | чуть ниже `building` | `building` | чуть выше `building` |
| power line | без изменений | без изменений | без изменений |
| water polygon / landuse | без изменений | без изменений | без изменений |

Почему здания локально: в OsmAnd `building layer=+3` имеет order 13 и всё
равно остаётся ниже дорог. Если поднять все `building layer=1` в глобальную
надземную полосу, 4 830 крыш/навесов в Люксембурге начнут рисоваться поверх
дорог. Это не соответствует ни OsmAnd, ни привычной картинке.

### 5.2. Дерево слоёв

Сверху вниз:

```text
... подписи, значки, POI ...
[полоса layer > 0]          ← сюда же существующие bridge-слои
  highway main bridge ...
  highway main layer >=1
  track/path layer >=1
  railway all layer >=1
  river/canal/stream layer >=1
  barrier layer >=1

[поверхность]
  building layer >=1        ← локально, сразу над building
  building
  building layer <=-1
  ... текущие слои без изменений ...

[полоса layer < 0]          ← сюда же существующие tunnel-слои
  highway main layer <=-1
  track/path layer <=-1
  railway all layer <=-1
  river/canal/stream layer <=-1
  barrier layer <=-1
  rail tunnel
  highway main tunnel
  river/stream/canal tunnel

landcover / рельеф / подложка
```

Подземную полосу не обязательно ставить в самый низ: текущие туннели стоят
выше `wood`/`grass`, чтобы линии не исчезали под заливками. Разумно сохранить
это же положение.

### 5.3. Один файл + subset

Для каждой копии:

```text
./vector/highway_main.sqlite|layerid=0|geometrytype=MultiLineString|subset=CAST("layer" AS INTEGER) > 0
./vector/highway_main.sqlite|layerid=0|geometrytype=MultiLineString|subset=CAST("layer" AS INTEGER) < 0
```

Базовая копия:

```text
subset=CAST("layer" AS INTEGER) = 0 OR "layer" IS NULL
```

`CAST` проверен на SQLite через OGR:

- `layer > 0` — 160 объектов;
- `layer < 0` — 111;
- `layer = 0 OR IS NULL` — 72 653.

QGIS сохраняет такие `subset` в datasource и корректно открывает проект.
Шаблон уже использует этот механизм для `highway main overview`, поэтому
подход не новый.

Важно: `highway main overview` и `[blocking] highway main overview` тоже
должны получить `layer=0 OR NULL`, иначе после отказа от физического деления
они начнут читать надземные/подземные дороги.

### 5.4. Что поправить в подготовке

- `core/field_subset.py`
  - добавить `layer` в `BUILDING`, `TRACK`, `PATH` (для track/path поле
    сейчас теряется);
  - `WATER` — только если решите поддерживать `layer` у водных полигонов;
    для линий `river/canal/stream` поле и так попадает через
    `COMMON_FIELDS`.
- `core/road_packing.py`
  - `KEY_FIELDS["railway_all"] += ("layer",)`;
  - `KEY_FIELDS["stream"]`, `["stream_intermittent"] += ("layer",)`;
  - `KEY_FIELDS["power_minor_line"] += ("layer",)` — если поддерживать ЛЭП;
  - `AREA_KEY_FIELDS["building"] += ("layer",)`.
- `core/query_recipes.py`
  - убрать `split_layer(fields="highway_main")` при переходе на subset;
  - `highway_main_bridge`: `dissolve(["highway", "layer"])`, иначе `layer`
    теряется;
  - при желании поддержать `layer` у мостов — добавить копии/полосы и для
    `highway_main_bridge`.
- `core/oneway.py`, `core/highway_integrity.py`
  - `_file_names` больше не должен искать `_layer_1`/`_layer_-1`, если
    физического деления нет.
- `core/project.py`
  - `_is_empty_datasource` должен учитывать `subset=`: иначе копия с нулём
    объектов в полосе никогда не будет удалена;
  - после смены datasource у `highway main overview`/blocking добавить фильтр
    по `layer`.
- `automap.qgz`
  - добавить копии-полосы, проставить subset, перенести существующие
    `highway main layer >=1/<=-1` в глобальные группы;
  - проверить `minScale`/`maxScale`: сейчас копии дорог не имеют
    scale-based visibility, а базовый слой имеет — при клонировании стиля это
    нужно решить осознанно.

## 6. Замеры скорости

Машина во время замеров была загружена другими сессиями (load average 6–7),
поэтому абсолютные секунды шумные; относительные пары и микрозамеры чтения
стабильнее.

### 6.1. Подготовка

| Операция | Время |
|---|---:|
| `highway_main`, обычное сохранение 72 тыс. | 0,55 с |
| `highway_main`, деление на 3 файла | 0,67 с |
| `building`, обычное сохранение 1 млн, 6 полей | 63,3 с, 153 МБ |
| `building`, дополнительно `layer>0` | +1,7 с, 0,7 МБ |
| `building`, дополнительно `layer<0` | +1,3 с, 0,03 МБ |

Вывод: физическое деление не катастрофа по времени, но требует аккуратного
порядка с упаковкой. `subset` даёт те же render-свойства и не добавляет ни
секунды подготовки.

### 6.2. Чтение с subset

| Вариант | 22 986 зданий |
|---|---:|
| без subset | 0,65–0,66 с |
| `layer=0 OR NULL` | 0,63–0,66 с |
| `layer>0` (148 объектов) | 0,05–0,08 с |

Фильтр практически бесплатен.

### 6.3. Кадр 1:100 000, 1200 px, Люксембург

| Вариант | Время кадра |
|---|---:|
| базовый шаблон, 3 физических файла дорог | 7,98–8,07 с |
| те же 3 слоя, но один файл + subset | 7,64–8,23 с |
| один объединённый слой дорог, без `orderBy` | 8,04–9,16 с |
| один слой дорог + `orderBy` | 8,17–8,92 с |

По кадру разница в пределах шума. Но изолированное чтение показывает, что
`orderBy` на больших слоях будет расти линейно с числом объектов, а `subset` —
нет.

### 6.4. Стоимость копий

В текущем шаблоне при 1:100 000:

- `highway main` — 0,23 с;
- `highway main layer >=1` — 0,03 с;
- `highway main layer <=-1` — 0,03 с.

То есть 10–15 небольших копий-полос дадут ориентировочно +0,3–0,8 с к кадру.
Это заметно, но приемлемо; главное — не добавлять полосы для объектов, где
`layer` почти не встречается (ЛЭП, водные полигоны, landuse).

Шаблон при этом вырастет примерно на 4–7 МБ XML: копия стиля дорог — ~1,1 МБ,
остальные стили меньше.

## 7. Этапы внедрения

### Этап 1 — минимальный и самый полезный

- Перенести существующие `highway main layer >=1` и `<=-1` из группы
  `highway main` в глобальные группы мостов/туннелей.
- Добавить `layer=0 OR NULL` в `highway main overview` и blocking-копии.
- Это не требует ни новых данных, ни новых слоёв, но исправляет главные
  нарушения: надземная дорога перестаёт быть ниже поверхности железной
  дороги, подземная — выше зданий и воды.

### Этап 2 — остальные основные объекты

- Добавить копии для `railway all`, `barrier`, `building` (building —
  локально).
- По желанию — `river/canal/stream` и `track/path`.
- Добавить `layer` в ключи упаковки и в `field_subset`.
- Научить `clean_project_layers` удалять пустые subset-копии.
- Добавить тесты на порядок слоёв и на то, что base + positive + negative даёт
  все объекты.

### Этап 3 — точные значения ±2/±3

- Сейчас в трёх полосах `layer=2` и `layer=1` попадают в одну копию, и их
  взаимный порядок произволен.
- Если это важно, добавить полосы `>=2` и `<=-2` (пять полос). В Люксембурге
  таких дорог 13, зданий — десятки, так что дополнительные слои почти всегда
  будут пустыми и удалятся при сборке.
- Альтернатива для маленьких копий — включить `orderBy` по `layer` только в
  копиях `>0`/`<0` (сотни объектов), но не в базовых слоях.

## 8. Что проверять

- `compare_projects.py`: геометрия не должна измениться, должны измениться
  только состав/ключи упаковки.
- Пиксельный A/B на Люксембурге и Альпах при 1:25k, 1:50k, 1:100k, 1:250k:
  отличия должны быть локальными, у мест с `layer≠0`, а не по всей карте.
- Профиль кадра: дополнительные слои не должны добавить больше ~0,5–0,8 с на
  1:100k.
- Память: `orderBy` не должен появиться на базовых слоях.
- Пустые копии: проект без `layer>0` не должен тащить пустой QGIS-слой.
- Старые проекты: они продолжают работать со старыми файлами; новый шаблон
  применяется только к новым сборкам.

## 9. Тесты, которые стоит добавить

- `FieldSubsetTest`: `PATH`, `TRACK`, `BUILDING` сохраняют `layer`.
- `RoadPackingTest`: `layer` входит в ключ `railway_all`, `stream`,
  `stream_intermittent`, `power_minor_line`, `building`; объекты с разным
  `layer` не сливаются.
- `LayerSubsetTest`: на синтетическом SQLite `base + positive + negative`
  даёт все объекты; `CAST`-выражения корректны для `null`, `0`, `-1`, `2`.
- `TemplateLayerOrderTest`: положительные копии выше всех поверхностных
  слоёв, отрицательные — ниже; `building`-копии остаются локальными.
- `EmptySubsetLayerTest`: копия с нулём объектов удаляется из проекта.
- `BridgeDissolveLayerTest`: `highway_main_bridge` сохраняет `layer` после
  dissolve.
- Опционально `LayerCopyStyleTest`: стиль копий совпадает с базовым (сейчас
  копии дорог уже расходятся: 105 правил у базы против 120 у копий).

## 10. Риски и открытые вопросы

- Копии стилей в шаблоне легко расходятся с базовым слоем. Текущие копии
  дорог уже содержат мёртвые полосы 300k+ и правила LOD, которых нет в базе.
  Нужен тест на совпадение или генерация копий из базового стиля.
- `subset` — провайдеро-зависимый механизм. На SQLite/GDAL 3.x проверен, но
  перед релизом стоит прогнать на Windows-сборке QGIS.
- Перенос дорог в глобальные полосы изменит картинку на пересечениях. Нужен
  пиксельный A/B и проверка подписей: порядок регистрации подписей и
  blocking-слоёв тоже меняется.
- `layer` у мостов с `bridge=yes` и у туннелей с `tunnel=yes` конфликтует с
  текущими отдельными слоями. Сейчас приоритет у `bridge`/`tunnel`; для
  строгой семантики нужно решить, что важнее при `bridge=yes layer=-1`.
- Водные полигоны и landuse не рекомендуется трогать: `layer` там редок, а
  dissolve/упаковка теряют поле.
- ЛЭП (`power`) уже рисуются выше всего; поддержка `layer` для них даст мало
  и потребует менять dissolve.

## 12. Итог

Глобальный `layer` в xtopo реализуем, но только через дополнительные
QGIS-слои-полосы. Наиболее выгодный по скорости и трудозатратам путь — три
глобальные полосы, один SQLite-файл на слой и `subset`-копии; `orderBy`
оставить только для маленьких копий, а физическое деление — как запасной
вариант.
