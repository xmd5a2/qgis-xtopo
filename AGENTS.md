# AGENTS.md — qgis-xtopo

## Что это

- Плагин QGIS (не приложение и не библиотека), минимум QGIS 3.28. Готовит
  данные OSM и рельефа (SRTM) и собирает проект QGIS из шаблона `automap.qgz`.
  Старый Docker-пайплайн лежит в `legacy/` только для справки.
- Корень репозитория — корень пакета: при установке каталог называется
  `qgis_xtopo`, поэтому импорты в тестах идут как `qgis_xtopo.core...`
  (`tests/__init__.py` регистрирует пакет).
- Плагин самодостаточен: только QGIS и его Python, без pip-зависимостей и
  системных утилит. Исключение — поставляемый `vendor/osmium/`; без него
  плагин обязан работать, только медленнее (`core/osmium_prefilter.py`).

## Команды

```sh
./tools/run_tests.sh                      # все тесты, offscreen, ~20 с
./tools/run_tests.sh tests.test_project   # только выбранный модуль (можно несколько)
python3 tools/build_plugin.py             # dist/qgis_xtopo-<версия>.zip + dist/qgis-xtopo-ready/
python3 tools/build_plugin.py --install   # + установка в профиль QGIS
./tools/run_qgis.sh                       # сборка + установка + QGIS с открытой панелью
WINEPREFIX=~/.cache/wineprefix-inno ./installer/build-installer.sh  # Windows-инсталлятор
QT_QPA_PLATFORM=offscreen python3 tools/check_pbf_coverage.py       # сверка полноты с osmium
```

- После изменения поведения: тесты зелёные → `build_plugin.py --install` →
  `installer/build-installer.sh`. Инсталлятор собирается всегда, даже если
  правка не про Windows: он содержит ту же копию плагина.
- При смене версии правьте `metadata.txt` **и** `#define MyAppVersion`
  в `installer/qgis-xtopo.iss`.
- Тесты — `unittest`. `tools/run_tests.py` запускает каждый модуль отдельным
  процессом: QGIS не переносит два приложения в одном процессе.
  `QT_QPA_PLATFORM=offscreen` уже выставлен. Запускайте имена модулей, а не
  отдельные классы: часть тестов создаёт `QgsApplication` в `setUpClass`, и
  класс, запущенный первым, может упасть на `QFontDatabase`.
- Интеграционные тесты с PBF пропускаются, пока `QGIS_XTOPO_TEST_PBF` не
  указывает на локальный `.pbf`. `check_pbf_coverage.py` дополнительно ждёт
  выгрузки Geofabrik в `~/qgis_projects/qgisxtopo-cache/geofabrik`.
- CI тесты не запускает: workflows собирают только Windows-инсталлятор и
  бинарники osmium.
- **QGIS для новых пользователей ставится официальным сетевым установщиком
  OSGeo4W** (`installer/scripts/install-qgis.ps1`): пакет `qgis-ltr` с
  зависимостями (~410 МБ, против 580 МБ у standalone-MSI) в
  `%LOCALAPPDATA%\OSGeo4W`; если он не сработал — запасной путь через
  standalone-MSI. Раскладка OSGeo4W отличается от standalone: приложение —
  `bin\qgis-ltr-bin.exe` (в standalone — `bin\qgis-bin.exe`), запускать
  надо через `bin\qgis-ltr.bat` (он задаёт переменные окружения, без них
  `qgis_app.dll` не грузится), значок — в `apps\qgis-ltr\icons\QGIS.ico`.
  Проверка установки — `installer/scripts/check-qgis-install.py`, прогон в
  CI — `.github/workflows/verify-qgis-install.yml` (вручную: качает
  ~410 МБ).
- **Вопрос в инсталляторе задаётся из `NextButtonClick`, а не из
  `CurPageChanged` и не из `InitializeSetup`.** Из `CurPageChanged` после
  ответа мастер сразу завершается, а из `InitializeSetup` вопрос
  появляется до окна мастера и прячется за другими окнами. Рабочее место
  — нажатие «Далее» на странице выбора каталога (`wpSelectDir`): окно
  уже видно, мастер после ответа продолжает работу.
- **Успех установки QGIS проверяется по факту, а не по коду возврата.**
  В wine `powershell.exe` — заглушка: молча ничего не делает и выходит
  с кодом 0, поэтому установщик считал, что QGIS установлен, и молчал.
  Теперь инсталлятор после запуска скрипта проверяет, появился ли QGIS,
  и есть ли журнал скрипта, и показывает ошибку с указанием причины.

## Структура и поток данных

- `core/pipeline.py` — оркестрация. Источники OSM (`geofabrik.py`,
  `overpass_*.py`, `sources.py`) → вырезка `osmium_prefilter.py` → чтение
  `pbf_source.py` → раскладка по слоям (`query_recipes.py`,
  `resources/queries/`) → рельеф `terrain.py` → чистка пустых слоёв.
  `core/project.py` собирает проект из шаблона в начале и удаляет пустые слои
  в конце.
- `core/terrain_cache.py` — кэш DEM/изолиний; `core/transliteration.py` +
  `map_language.py` — язык карты; `core/i18n.py` + `resources/lang/en.json` —
  язык интерфейса; `core/expressions.py` — регистрация выражений QGIS;
  `core/measure.py` — размеры рамки; `core/peak_placement.py` — правило
  проверки пиков; `core/peak_filter.py` — его применение к слою `peak`.
- `gui/dockwidget.py` — вкладки «Данные/Слои/Рельеф»; `gui/projectpanel.py` —
  вкладка открытого проекта, атлас и слои.
- **Штатные инструменты QGIS** (измерение, identify) вызываются через `QAction`
  по `objectName`: `mActionMeasure`, `mActionMeasureArea`,
  `mActionMeasureAngle`, `mActionMeasureBearing`, `mActionIdentify`. В
  Python-обёртках QGIS 3.44 классов измерения нет
  (`gui/projectpanel.py: _trigger_qgis_action`). Закрытие окна
  `QgsMeasureDialog` не снимает инструмент с холста, поэтому панель ловит
  `QEvent.Close` и включает `QgsMapToolPan` (`_connect_measure_dialogs`).
- **Подписи размеров** — `core/measure.py` по эллипсоиду WGS84; в окне охвата
  они берутся у `MeasuredCanvas.set_frame_provider` при каждой отрисовке.
  Шкала масштаба считается от ширины видимой области, а не от знаменателя
  масштаба (`gui/extentdialog.py: scale_bar`).
- **Окно выбора охвата**: поиск места по Nominatim (`core/nominatim.py`) и
  выбор подложки предпросмотра (`BASEMAPS` в `gui/extentdialog.py`).
  Подложка меняет только карту в окне, в готовую карту не попадает.
  Nominatim: не больше одного запроса в секунду, обязателен User-Agent,
  ответы кэшируются по строке запроса (`core/nominatim.py`).
- **Enter в окне охвата**: в строке поиска он запускает поиск, а не закрывает
  окно. `QLineEdit` отдаёт Enter родителю, поэтому `keyPressEvent` окна
  проверяет фокус и не применяет охват (`gui/extentdialog.py`).
  Shortcut Enter живёт на холсте (`Qt.WidgetShortcut`), иначе он перехватывал
  бы ввод в строке поиска.
- **Поток поиска — не ребёнок окна**: окно закрывается во время запроса,
  поток должен доработать и удалиться сам (родитель — `QgsApplication`);
  на `aboutToQuit` его ждёт `shutdown_nominatim_workers`.
- **Перед удалением панели все QThread останавливаются.** QThread нельзя
  уничтожать, пока он работает, иначе QGIS падает с «QThread: Destroyed
  while thread is still running». `XtopoDockWidget.shutdown_workers`
  отменяет и ждёт pipeline, PBF, Geofabrik, DEM, Sonny, прокси и серверы;
  вызывается из `closeEvent` (`final=False`, панель можно открыть снова),
  `unload`, `destroyed` и `aboutToQuit`. Новые фоновые потоки добавлять
  только с отменой и ожиданием в этом методе. **Не объявлять в QThread
  свой сигнал `finished`** — он перекрывает встроенный, по которому
  `deleteLater` удаляет поток; удаление до возврата из `run()` даёт то же
  падение. У `PipelineWorker` сигнал называется `completed`; удаление
  повешено на встроенный `QThread.finished`. Проверка —
  `test_pipeline_worker_does_not_shadow_qthread_finished` в
  `tests/test_ui_panels.py`.
- `automap.qgz` лежит только в корне; путь в коде — `core/resources.py:
  template_path()`. При сборке копируется в пакет как
  `resources/automap.qgz`. Рядом не оставлять `*.bak*`.
- `dist/`, `output/`, `installer/payload/`, `__pycache__/`,
  `resources/automap.qgz` — артефакты, не редактировать.

## Ограничения

- **Git**: после каждой законченной feature (не тестовой!) делать коммит с осмысленным комментарием
  на английском. Без явной просьбы не делать `push`, `checkout`, `reset --hard`, `stash`.
- **Стиль — только в `automap.qgz`**. Инструментов правки шаблона и переноса
  стиля в готовые проекты нет (не возвращать `tools/patch_template_*.py`).
  `core/project.py: repair_project` при открытии лишь убирает пустые слои,
  чинит шрифт и оборачивает `overlay_*` в `try(...)`, но стиль не обновляет.
  Изменили стиль — переготовьте данные.
- **Пустые слои** вырезаются при сборке; обращение `overlay_*` к
  отсутствующему слою даёт NULL и скрывает объекты. Поэтому такие фильтры
  обёрнуты в `try(..., запасное значение)` (`patch_overlay_filters`).
- **Панель ≤ 600 px по высоте** — тест `test_dock_is_compact`
  (`tests/test_pipeline_integration.py`). Сжимайте spacing/высоту, а не тест.
- **Строка статуса — `WrappedLabel`, высота не фиксирована**: длинный
  прогресс Geofabrik с ETA переносится и не обрезается. Прогресс
  (`Загрузка карт:`) не проходит через `_short_status`, иначе обрежется
  хвост с расчётным временем.
- **Сетевой предохранитель — `core/net.py`.** Все сетевые запросы плагина
  идут через urllib-opener с обёрткой `GuardedOpener`: ошибка соединения
  ставит глобальный запрет на ~20 с (`OFFLINE_TTL`), пока он действует,
  запросы падают сразу; успешный запрос или `net.reset()` (кнопка
  обновления, смена прокси) запрет снимают. Ответ сервера с кодом ошибки
  (HTTPError) запрета не ставит. Opener подставляет `DEFAULT_TIMEOUT`, если
  вызывающий код таймаут не задал. Ставится в `proxy.apply()` и для
  `dem_sources._OPENER`.
- **Прокси — `core/proxy.py`.** Кнопка в углу вкладок открывает диалог;
  `proxy.apply()` ставит opener urllib (через предохранитель), opener
  dem_sources и `QNetworkProxy`. Статус значка: `proxy.probe()` (TCP +
  приветствие SOCKS5 с авторизацией, без внешней сети) в фоновом
  `ProxyCheckWorker`, панель проверяет при показе и раз в 30 с; пока панель
  скрыта, проверки нет. Живой прокси в тестах — только через
  `QGIS_XTOPO_TEST_PROXY`, без него тест пропускается.
  Значок рисуется сам (`_proxy_state_icon` в `gui/dockwidget.py`):
  контур глобуса цветом текста и маленькая точка состояния в правом
  нижнем углу — зелёная/красная; без прокси точки нет. Не заливать
  стандартную иконку сети цветом состояния: в части стилей глиф плотный,
  и после SourceIn остаётся сплошное пятно. Проверка —
  `ProxyIconTest` в `tests/test_ui_panels.py`.
- **Кэш Geofabrik не обновляется сам.** Валидный локальный PBF
  (`ensure_maps`) используется как есть: ежедневная регенерация выгрузок
  не причина перекачивать карты. Свежую выгрузку получают удалением файла
  из `<проекты>/qgisxtopo-cache/geofabrik`.
- **Рельеф в pipeline — две стадии.** `prepare_terrain_raster` (скачивание
  тайлов, сборка DEM, затенение) не зависит от слоёв и в `run_project`
  работает в потоке `xtopo-terrain` параллельно `Pipeline.run`; ошибки из
  потока собираются в список и всплывают после `join`, отмена проверяется
  там же, в `finally` поток дожидается. `prepare_terrain_isolines` ждёт
  ключ кэша DEM от первой стадии и идёт после слоёв — контуры режутся по
  воде и ледникам (`_water_mask_paths`, `_glacier_polygons` читают
  `vector_dir`). `prepare_terrain` остался как последовательная обёртка
  обеих стадий.
- **Рабочие данные пользователя** (`~/qgis_projects/...`, кэш Geofabrik) не
  использовать как тестовые полигоны; чтение и offscreen-открытие допустимы.
- **Слои обрабатываются параллельно, по умолчанию 3/4 ядер с потолком 8**
  (`core/cpu.py: cpu_workers`, `Pipeline._worker_count`). На 16 ядрах 12
  слоёв оказались медленнее восьми: конкуренция за диск и память. На
  четырёх ядрах будет 3 воркера, на восьми — 6. `parallel_workers` в
  `config.ini` задаёт число явно. Остальные CPU-задачи (osmium, окна COG,
  проверка пиков) тоже берут 3/4 ядер; у проверки пиков потолок 4 —
  больше потоков упираются в GIL и работают медленнее.

## Шаблон и стили

- **Порядок туннелей**: слои `rail tunnel`, `highway main tunnel`,
  `river tunnel`, `stream tunnel`, `canal tunnel` идут подряд сразу под
  `[TERRAIN] isolines glacier` — под всеми линейными слоями (включая
  изолинии), над фоновыми площадными (карьер, ледник, лес). Проверка —
  `TunnelLayerOrderTest` в `tests/test_template_styles.py`. Площадные слои
  середины стека (вода, болото) остаются над туннелями, как и раньше.
- **Границы admin_level выше воды.** Слои `admin level 2 (country
  borders)` / `country names` и группа `admin level 4` (линии и подписи)
  идут в дереве выше группы `water`. Иначе вода закрывает линии границ,
  а подписи QGIS всё равно рисует поверх — они остаются без линии и
  выглядят висящими в воздухе. Проверка — `AdminBoundaryOrderTest` в
  `tests/test_template_styles.py`.
- **Варианты крутых склонов**: `[TERRAIN] slope (steep) var1/var2/var3` на
  общей подложке `slope_upscaled.tif`, показывается один. Привязка строго по
  полному имени (`STEEP_VARIANTS`, `LAYER_NAMES` в `gui/projectpanel.py`);
  другие слои с «var1» вариантами не являются, а переименование слоя в
  шаблоне ломает панель. Выбор — кнопка с меню, не выпадающий список: в узкой
  панели он обрезает названия. При открытии проекта вариант ставится
  автоматически по типу рельефа (`core/slope_style.py`): 90-й процентиль
  уклона из `raster/slope_upscaled.tif` — от 30° горы (var1), 12–30°
  предгорья (var2), ниже 12° равнины (var3). Видимость слоёв при этом не
  меняется, ручной выбор пользователя в том же проекте сохраняется. Растр
  читается выборкой 1200×96 пикселей (~10–15 мс): у полосового TIFF каждая
  строка читается целиком, поэтому высоту выборки уменьшать нельзя, а
  ширину можно.
- **Варианты отмывки рельефа**: `[TERRAIN] hillshade var1/var2` на общей
  подложке `hillshade_composite.tif`. var1 — светлый фон для равнин:
  прозрачность 0 при значении 190 (плоскость), тени темнее, а освещённые
  склоны получают лёгкий серый полутон, чтобы не терять их рельеф. var2 —
  прежняя отмывка gdaldem для гор. Показывается один слой, по умолчанию
  var1; выбор — кнопка с меню рядом с «Затенением». Подпись сокращена,
  чтобы кнопка помещалась в узкой панели. Привязка по полному
  имени; `[TERRAIN] hillshade` остаётся запасным именем для старых проектов.
  Меняя параметры отмывки, обновляйте точку 190 в шкале var1 и
  `HILLSHADE_STYLE_VERSION`.
- **Фаза штрихов изолиний**: `offsetAlongLine` должен лежать внутри карты
  `properties` блока `data_defined_properties`. Свойство рядом с картой QGIS
  не читает, и штрихи выстраиваются колонками. Проверка —
  `tests/test_template_styles.py`.
- **Изолинии режутся по воде и ледникам растровой маской**
  (`terrain.py: generate_isolines`, `_try_mask_water`, `_try_mask_glaciers`):
  полигоны воды и ледников записываются в копию DEM значением nodata,
  `gdal.ContourGenerate` с `useNoData=1` обрывает контуры у границ ещё
  при генерации. Прежнее векторное срезание (Union всех озёр и
  `Difference` каждой линии) стоило ~74 с на регионе Женевского озера
  против ~1 с маски. Ледниковые изолинии — отдельный проход по растру,
  очищенному от всего, кроме ледников (`keep_only=True`), тоже без
  векторного деления. Запасной векторный путь (`_subtract_water_from_layer`,
  `_split_isolines_by_glaciers`) остался для тайловой нарезки и сбоев
  маски. Расхождение с прежним кроем — до ~2 пикселей DEM у кромки воды.
- **Треки на 1:50 000+**: в правилах слоя `track` для
  `highway_integrity='3'` должен быть символ в каждом диапазоне масштаба.
  Пропуск этой ветки оставлял треки с таким значением без отрисовки.
  Диапазоны 50k+ дополнительно фильтруются по `@level_of_detail`
  (50–100k ≥3, 100–200k ≥3, 200–300k ≥4, 300k+ ≥5). Проверка —
  `TrackScaleTest`.

## Подписи и язык карты

- Язык карты — переменные проекта. **Пустое значение переменной удаляется**,
  `@name_pref_suf_lang` становится NULL, QGIS не вызывает функцию подписи, и
  названия исчезают. Защита внутри выражений не помогает: QGIS до них не
  доходит.
- `@name_pref_suf_lang` равен `ru` даже при «Местных названиях»: тип объекта
  сокращается по-русски всегда («ледник» → «л.», «брод» → «бр.»).
- `level_of_detail` — переменная, на которой держатся фильтры отрисовки во
  многих слоях (дороги, тропы, родники). Без неё правила ложны. Панель: 3–6,
  по умолчанию 4, ключ `SETTINGS_KEY_DETAIL`; в новый проект попадает через
  `project.py: _set_detail_variable`.
- `pick_name_part` (`core/transliteration.py` +
  `resources/expressions/transliterate.py`): берёт кириллическую часть,
  помеченную языком (`ru: ...`) или скобками с той же строкой другой азбукой;
  скобки-уточнения (`Mersedes Benc (грузовой)`) название не заменяют. Дефис
  внутри слова не делит, тире с пробелами делит. При `script="local"`
  название выводится целиком.
- Русский тип объекта (`л.`, `м.`, `хр.`, `ур.`) приписывается только
  кириллическому названию (`_has_cyrillic` в `resources/expressions/
  format_*.py`). Название из одного слова типа не дополняется префиксом.
  Списки типовых слов у водной и населённой групп должны совпадать.
- **«(неж.)» у населённых пунктов** скрывается по тем же условиям, что
  категория сложности перевала: пометка не приписывается имени не
  кириллицей на нерусской карте, включая «Местные названия»; на русской
  карте и для кириллических имён она остаётся. Проверка — тесты
  `uninhabited_place` в `tests/test_label_abbreviations.py`.
- Выражения (`readable_name`, `format_place_name`, `pick_name_part`, ...)
  регистрируются `core/expressions.py: load_expressions()`. Если функции нет,
  QGIS не рисует подписи. Доступные функции — `registered_functions()` через
  `QgsExpression.Functions()`; `registeredFunctionNames()` в QGIS нет.
- **Название острова не должно вытесняться пиком**: у подписей островов
  (`island polygon`, `island point names`) `priority=7`, у пиков — `6`.
  Иначе пик занимает место, и имя острова не размещается. Проверка —
  `tests/test_template_styles.py`.
- **Вытеснение значков POI действует и внутри слоя.** Фильтр подавления
  скрывает значок, если рядом есть точка с меньшим рангом **или с тем же
  рангом, но меньшими координатами**. Без второго условия значки одного
  слоя (населённые пункты, хижины) на мелких масштабах накладывались бы
  друг на друга; победитель кластера остаётся в служебном слое
  (`_prune_band` в `core/poi_icons.py`). **`geometry(@parent)` в
  `overlay_nearest` не работает** — `@parent` доступен только в
  `aggregate`, внутри аргументов overlay он NULL (проверено на QGIS
  3.44). Поэтому родительская точка передаётся через
  `with_variable('pg', $geometry, ...)`, а `overlay_nearest` возвращает
  массивы `array(x($geometry), y($geometry), rank)`. Приоритет и точное
  расстояние в метрах считаются снаружи вызова через `array_filter` с
  `@element`; `max_distance` — только градусный конверт для индекса.
  Размер значка — видимая часть SVG (`_svg_content_scale`: рендер в
  QImage и bbox по альфе), а не весь холст: у пика рисунок занимает
  ~72 %, у станции подъёмника ~78 %, и прозрачные углы не должны
  скрывать соседей. Фильтры запечены в шаблон; при перегенерации
  кавычки в XML экранировать (`&quot;`), иначе файл ломается.
  Проверки — `PoiSuppressionExpressionTest`,
  `test_icon_rules_break_ties_within_a_layer`, `PoiPruneTest` в
  `tests/test_template_styles.py`.
- **Значки на линиях и полигонах — препятствия для POI.** У мостов
  значок рисуется `MarkerLine` с `CentralPoint`, у кладбищ —
  `CentroidFill`; фильтр правила скрыл бы весь мост или площадку.
  В служебный слой добавляется одна точка на объект (середина линии или
  `pointOnSurface`) с рангом меньше 1 — выше любого POI
  (`read_template_obstacles`, `_icon_anchor`). Ленты стрелок и ЛЭП не
  обрабатываются: у них значков вдоль линии много, одна точка в
  середине соврала бы. `_prune_band` сравнивает расстояние с размером
  значка **того объекта, который будет скрыт**, а не с глобальным
  максимумом, иначе в служебный слой попадала половина мостов.
  Проверки — `PoiObstacleTest` в `tests/test_template_styles.py`.
- **Значки мостов одного слоя вытесняют друг друга.** Линия и значок
  моста рисуются разными правилами: исходное правило оставляет только
  `SimpleLine`, а значок вынесен в отдельное правило на каждый
  канонический диапазон масштаба. QGIS рисует все совпавшие правила,
  поэтому `_RuleEvaluator._descend` возвращает максимальный размер
  значка среди подходящих листьев: иначе правило линии (size 0) скрывало
  бы значок. При подготовке данных `_write_icon_hide` пишет в слои
  мостов поле `icon_hide` — индексы диапазонов, где рядом есть мост того
  же слоя с меньшими координатами (`_hidden_bridge_bands`). У
  `MarkerLine` маркерного правила задано data-defined `enabled`
  (`poi_icons.icon_enabled_expression`): false, если диапазон есть в
  `icon_hide`, иначе true. Свойство `enabled` отключает только значок,
  линии остаются. **`overlay_nearest` в data-defined свойствах символа
  вешает отрисовку — не использовать.** Побеждает объект с меньшими
  координатами, как у точечных POI; `_prune_band` не берёт скрытые
  значки в служебный слой. У `highway main bridge` service-мосты на
  200k+ остаются линиями, но без значка (у символа 200000–300000 удалён
  `MarkerLine`, маркерных правил для него нет), поэтому на 1:200000 и
  мельче их значки не появляются. Проверки —
  `BridgeIconSuppressionTest`, `BridgeIconHideTest` в
  `tests/test_template_styles.py`.
- **Все слои со значками — только EPSG:4326, имена служебных слоёв не
  повторяются.** Точное расстояние подавления считается в метрах по
  координатам кандидатов, поэтому все слои должны быть в градусах;
  слой в EPSG:3857 дал бы неверные метры. Поэтому рецепты
  `mountain_pass`, `railway_station_icons`, `railway_halt_icons`,
  `aerialway_station` не должны заканчиваться `reproject()` (проверка —
  `PoiRecipeCrsTest` в `tests/test_pipeline_logic.py`). Служебных
  файлов один — `poi_icons.gpkg`; прежний `poi_icons_3857.gpkg`
  удаляется при сборке. Два слоя с одинаковым именем «poi icons N»
  (было: 4326 и 3857) делали выбор `overlay_nearest` неоднозначной —
  первым находился слой не той системы координат, и вытеснение не
  работало вовсе. Проверка —
  `test_service_layer_names_are_unique_and_referenced` и
  `test_all_icon_layers_use_one_crs` в `tests/test_template_styles.py`.
- **Линии подъёмников на масштабах 1:100000+ серые.** В слоях
  `aerialway cable car, gondola` и `aerialway chair lift` символы 2
  (100000–300000) и 3 (300000+) рисуют штриховую линию серым
  `85,85,85`, а центральную линию и стрелки направления — светлее,
  `105,105,105` (на масштабах крупнее 1:100000 линии остаются
  чёрными/тёмно-серыми, как раньше).
- **`aerialway=goods` — отдельный тонкий серый стиль.** В слое
  `aerialway cable car, gondola` правила cable_car/gondola отбирают
  только эти два типа, а `goods` рисуется сплошной линией
  `105,105,105` толщиной 0,22/0,20/0,18 мм и только до 1:200000
  (`scalemaxdenom="200000"`, на 300k+ правила нет). Маркеров и стрелок
  у goods нет. Проверка — `AerialwayGoodsStyleTest` в
  `tests/test_template_styles.py`.
- **Хутора и отдельные дворы видны до 1:200000.** В слое `places main`
  ветки `hamlet` и `isolated dwelling` (и значки, и подписи) заканчиваются
  на `scalemaxdenom="200000"`; верхняя граница в QGIS исключающая, поэтому
  на 1:200000 их уже нет, а на 300k+ правил нет вовсе. Тег `population`
  ограничение не обходит: в ветке `by population` (рендерер и подписи)
  стоит `AND NOT (place IN ('hamlet','isolated_dwelling') AND
  @map_scale >= 200000)`, такие пункты уходят в типовую ветку, где правил
  на этих масштабах нет. Ниже 200k стиль по населению сохраняется.
  Проверка — `SettlementScaleTest` в `tests/test_template_styles.py`.
- **Два уровня сервисных дорог.** Во всех слоях `highway main*`
  (включая bridge/tunnel и копии для `layer`) обычный `highway=service`
  без `service=*` виден до 1:300000 (100–200k — `@level_of_detail >= 3`,
  200–300k — `>= 4`, на 300k+ правила нет). Дороги с `service=*`
  скрываются раньше: 50–100k — `>= 4`, на 100k+ правил нет; ветка
  `service driveway` (driveway/parking_aisle/alley) имеет те же сроки.
  Это действует и для мостов (`bridge=yes`), и для туннелей
  (`tunnel=yes`). Где у 100k–300k один и тот же символ (туннели, зимние
  дороги), диапазон не делят на два правила: QGIS теряет символ у
  второго, поэтому LOD проверяется через `@map_scale` внутри одного
  фильтра. Проверка — `ServiceRoadLodTest`.
- **Пересыхающие водотоки на 1:100000 и мельче тоньше постоянных.**
  В слое `stream intermittent` ветка `default` на 100–200k, 200–300k и
  300–500k имеет ширину 0.12 мм (у `stream` — 0.16). У
  `river intermittent` и `canal intermittent` на 100–300k ширина
  0.22 против 0.29, на 300k+ — 0.17 против 0.23. На более крупных
  масштабах ширины не меняются. Проверка —
  `IntermittentWaterwayWidthTest` в `tests/test_template_styles.py`.

## Источники рельефа

- **Единый список источников — `core/dem_sources.py`.** Ключи: `auto`
  (по умолчанию), `srtm`, `cop30`, `nasadem`, `alos`, `3dep`, `sonny`,
  `manual`. Там же описание для интерфейса, покрытие, атрибуция и проверка
  доступности.
- `Config.terrain_source` хранит ключ; `resolved_terrain_source()` понимает
  старые `config.ini` без этого поля (`get_terrain_tiles=true` → `manual`,
  иначе `srtm` — это `LEGACY_DEFAULT_SOURCE`). В `config.ini` пишется явный
  ключ, у новых проектов — `auto`.
- **Доступность проверяется сразу после изменения охвата, в фоне и до
  открытия вкладки «Рельеф»** (`DemAvailabilityWorker` в
  `gui/dockwidget.py`). Наборы без данных для охвата отключаются в списке,
  а выбранный недоступный источник заменяется подходящим. Проверка идёт
  параллельно по всем наборам (`ThreadPoolExecutor` по числу источников),
  результат кэшируется в `_CHECK_CACHE` (успех 30 минут, ошибка 2 минуты);
  кнопка ⟳ у списка источников вызывает `check_availability(force=True)`.
- **Сбой сети не отключает набор**: `Availability(checked=False)` с
  сообщением «не удалось проверить». Для Copernicus при недоступном STAC
  покрытие проверяется прямыми HEAD-запросами к открытому зеркалу AWS
  (`_cop30_file_availability`).
- **STAC отвечает нестабильно**: системный DNS иногда возвращает адрес
  Azure Front Door с закрытым портом 443. `_MultiAddressHTTPSConnection`
  перебирает все адреса из ответа DNS, а если они не открылись — берёт
  A-записи у публичных резолверов (UDP DNS, затем DoH) и пробует их;
  рабочий адрес запоминается на сеанс.
- **Режим «Автоматически» (`AUTO_SOURCE`) — это не набор, а подбор по
  тайлам 1°×1°.** Приоритет `AUTO_PRIORITY`: `3dep` → `sonny` → `cop30`
  (фон) → `srtm` (`dem_sources.auto_plan`). В горных регионах между Sonny
  и Copernicus встаёт `alos` (`MOUNTAIN_PRIORITY`): 3DEP и Sonny остаются
  выше него. Горность определяется `core/relief.py` по встроенной сетке
  `resources/data/relief_grid.npz` (1°, минимум и максимум высоты из
  ETOPO5, ~194 КБ; ~0.02 мс на охват, без сети). Охват горный, если
  перепад высот ≥ 800 м хотя бы у 25 % тайлов суши; так Турция, Непал и
  Кавказ получают ALOS. Sonny покрывает Европу (`europe-1s`), поэтому
  Дания и Польша остаются на Sonny, а равнины вне его покрытия
  (например, степь Казахстана) — на Copernicus. Сетка пересобирается
  `tools/build_relief_grid.py`. Принудительного автовыбора
  3DEP больше нет: прежняя логика `preferred_source` осталась только для
  предупреждения `source_warning`, когда пользователь выбрал набор вручную.
- Мозаика собирается `terrain.download_auto_dem`: сначала каждый набор
  приводится к общей сетке отдельным слоем, затем `gdal.Warp` по списку
  слоёв, где **поздний источник перекрывает ранний, а его nodata не
  затирает ранние данные** (проверено). Разрешение мозаики — самый
  подробный шаг из входящих наборов, который влезает в `MAX_DEM_PIXELS`;
  иначе берётся более грубый шаг. `download_sonny_dem` — тот же код с
  приоритетом `sonny` → `cop30` → `srtm`.
- **Sonny DTM — один источник из нескольких наборов** (`core/sonny.py`):
  `at-05s`, `ch-05s` (0,5″), `europe-1s`. Набор 3″ (около 90 м) не
  используется: где нет 1″, фоном идёт Copernicus 30 м. Список тайлов
  берётся из Google Drive (`embeddedfolderview`, коллективным папкам нужен
  `resourcekey`), кэшируется на неделю в `~/.cache/qgis-xtopo/sonny` и
  обновляется в фоновом потоке при старте панели. Скачанные тайлы лежат в
  `<проекты>/qgisxtopo-cache/sonny/tiles`.
- Файлы Sonny — zip с одним `.hgt` без заголовка (big-endian int16,
  3601/7201/1201 точек). Драйвер SRTMHGT читает 1201 и 3601, для 7201
  нужна VRT-обёртка `sonny.hgt_vrt`. Вода и пустоты заполнены нулями, а не
  `-32768`, поэтому нули считаются данными.
- **Открытое зеркало Copernicus в AWS неполное**: у части тайлов есть
  только AUXFILES и XML. Адрес AWS используется, только если файл реально
  есть (HEAD), иначе ссылка из STAC подписывается (`sign_pc`). Если каталог
  STAC не ответил, покрытие Copernicus считается полным, а неоткрывшиеся
  тайлы пропускаются при сборке слоя.
- **Ручной GLO-30 с нехваткой тайлов**: `terrain._download_cop30` проверяет
  покрытие (`auto_coverage`); при полном покрытии идёт обычный
  `download_cog_dem` с кэшем окон, иначе тайлы раскладываются
  `cop30` → `srtm` и собирается мозаика. Сообщение о замене пишется в
  рантаймовое `config.terrain_fallback` (в `config.ini` не сохраняется),
  панель показывает его в `dem_warning`, журнал — отдельной строкой.
- **3DEP выбирается автоматически**, если покрывает всю сушу охвата
  (`dem_sources.preferred_source`). Суша определяется по Natural Earth из
  ресурсов QGIS (`resources/data/world_map.gpkg`, слой `countries`), а не
  по покрытию ALOS/Copernicus: те публикуют и океанские тайлы с нулевыми
  высотами. Если Natural Earth недоступен, используется покрытие
  ALOS/Copernicus, а при его отсутствии требуется покрытие всех тайлов.
  Ручной выбор другого источника для такого охвата даёт предупреждение
  (`source_warning`), «Свой каталог» не перетирается.
- **Разные системы высот в мозаике** (3DEP — NAVD88, Copernicus — EGM2008,
  SRTM — EGM96, Sonny — национальные) показываются предупреждением
  `mixed_datum_warning`: на границах тайлов возможны ступеньки. Для обычных
  наборов правило прежнее — один набор на проект.
- Для `cop30`/`nasadem`/`alos`/`3dep` доступность и список тайлов берутся
  из STAC Planetary Computer; для SRTM — по широтному покрытию
  −56…60°, для Sonny — по локальному каталогу тайлов, ручной каталог
  доступен всегда.
- Ограничения покрытия: у GLO-30 не опубликованы 25 тайлов (Армения,
  Азербайджан, СЗ Иран, Туркменистан), NASADEM только −56…61°, 3DEP —
  США, Канада и Мексика. Не предлагать эти наборы там, где данных нет.
- Растровые наборы читаются по HTTP Range через `/vsicurl` и сразу
  переводятся в локальное окно EPSG:4326 (`terrain.py: download_cog_dem`).
  Запас вокруг охвата `COG_PADDING = 0.002°`: тайлы Copernicus сдвинуты
  относительно целых градусов, без запаса у края остаётся полоса nodata.
  Окно ограничено `MAX_DEM_PIXELS` (120 млн пикселей); для больших охватов
  разрешение снижается, об этом пишется в журнал.
- **STAC отдаёт тайлы южнее и западнее запроса**: например, на окно
  3°×2° — 20 тайлов вместо 6. Объекты вне окна отбрасываются сразу
  (`terrain._item_overlaps`), иначе их ссылки подписываются и читаются
  при сборке мозаики впустую.
- **Удалённые COG перед мозаикой скачиваются параллельно**
  (`terrain._fetch_cog_windows`, число потоков — 3/4 ядер): каждый тайл
  отдельным `gdal.Warp` приводится к общей сетке с `dstNodata=-32768`,
  затем финальный warp собирает локальные файлы. Область вне тайла
  получает nodata, поэтому источники не перекрывают друг друга нулями;
  результат бит-в-бит совпадает с прямым warp'ом (проверено на ALOS,
  6 тайлов). Тайлы грубее `MAX_COG_PREFETCH_PIXELS` (3DEP 10 м) остаются
  на прямом `/vsicurl`, иначе предзагрузка читает сотни мегапикселей.
- **Журнал называет скачиваемый файл каждого тайла всех источников** —
  «Загрузка тайла рельефа: N46E006.hgt.gz (SRTM v3 (skadi), 30 м)»,
  «…Copernicus_DSM_COG_10_N46_00_E009_00_DEM.tif (Copernicus GLO-30)».
  Иначе параллельные загрузки неотличимы. SRTM — в `download_srtm`
  (terrain.py), растровые наборы — по имени URL в `_cog_sources`, Sonny —
  в `sonny.download_tile`.
- Кэш окон — `<проекты>/qgisxtopo-cache/srtm/cog/<источник>`; ключ включает
  охват. Меняя запас, формат окна или источник данных, поднимайте версию
  `v1` в `terrain.py: _cached_cog`, иначе старый кэш отдаст устаревшее.
  Перед загрузкой `terrain_input_dir` очищается, иначе в сборку
  попадут тайлы другого набора.
- **Одна вертикальная система на проект**: SRTM/NASADEM — EGM96,
  Copernicus/ALOS — EGM2008, 3DEP — NAVD88. Смешивать нельзя. ALOS — DSM,
  3DEP — DTM.
- Атрибуция источников пишется в переменную проекта `dem_attribution`;
  подпись макета атласа (рядом с OSM) выводит её через
  `[%if(@dem_attribution ...)%]`. `rewrite_project_archive` получает
  `dem_attribution` из выбранного источника. Рамка подписи — 210 мм: это
  предел переноса длинной строки, но видимый прямоугольник подгоняется
  по тексту (`ProjectPanel._fit_copyright_label` вызывает
  `adjustSizeToText()` при открытии проекта и перед экспортом). Иначе
  белая полоса тянется на все 210 мм.
- Строки доступности в панели короткие (`Availability.message`), полные
  формулировки — в `Availability.detail` и подсказке. Подпись в панели —
  `WrappedLabel`: высота считается по фактической ширине, иначе в узкой
  панели обрезается последняя строка с числом тайлов.
- Верхняя граница охвата не включает тайл, начинающийся ровно на ней:
  `tiles_for_bbox` использует `ceil(max) - 1`.

## Рельеф и кэш

- `terrain_cache.py` переиспользует DEM/изолинии, пока совпадают версия
  расчёта (`DEM_VERSION`, `HILLSHADE_STYLE_VERSION`, `ISOLINES_VERSION`),
  параметры (шаг, сглаживание, ресемплинг) и исходные данные. Версия
  плагина в ключ не входит: обновление интерфейса не должно пересчитывать
  DEM. Меняя формат результатов, добавляйте новые файлы в
  `DEM_FILES`/`ISOLINES_FILES` и поднимайте нужную версию, иначе старый
  кэш отдаст устаревшее.
- **Кэш рельефа проверяется до скачивания тайлов** — по подсказке
  `terrain_cache.dem_hint` (версия расчёта, область, источник, параметры;
  для ручного каталога и локальных тайлов — отпечаток файлов). Полный ключ
  требует хеша содержимого тайлов, а подсказка — нет, поэтому повторная
  подготовка не ходит в сеть и не собирает мозаику. Подсказки лежат в
  `terrain_result_cache_dir/dem-hints` (хранится `KEEP_HINTS` штук);
  `store_dem_hint` вызывается после `store_dem`. Если наборы/сообщение о
  замене тайлов должны переживать восстановление из кэша — добавляйте их
  в данные подсказки.
- **Восстановление растров из кэша не копирует лишнего**: файлы, которые
  уже лежат на месте с тем же размером и mtime, пропускаются, а
  `slope_upscaled.tif`/`hillshade_composite.tif` связываются жёсткой
  ссылкой (их удаляет `_clean_layers` перед каждым прогоном, поэтому
  запись в них невозможна). `merged_dem*` жёсткой ссылкой не связывать:
  их `_clean_layers` сохраняет, а при промахе кэша `build_dem` перезаписал
  бы кэш по ссылке.
- **Отмывка — как `gdaldem hillshade` по умолчанию**: солнце 315°/45°, без
  вертикального преувеличения, плюс 10 % подсветки теней
  (`terrain.py: generate_hillshade_slope`). Многонаправленная отмывка с
  `altitude=70`, `zFactor=2` и примешиванием уклона давала почти белое
  полотно. Меняя параметры, поднимайте `HILLSHADE_STYLE_VERSION` в
  `terrain_cache.py`, иначе кэш вернёт старую картинку. Шкала var1 в шаблоне
  привязана к «плоскому» значению 190: после изменения высоты солнца или
  подсветки теней её нужно сдвинуть.
- Оценка времени в панели (`dockwidget.py: _estimate_seconds`) считается от
  доли области в выгрузке (`pbf_fast.py: extended_ratio`), а не от общего
  числа объектов; прежняя формула завышала в 3–8 раз.

## Драйверы и osmium (частые потери данных)

- **Выключенное правило рендера съедает объекты**: в QGIS объект достаётся
  первому правилу, чей фильтр совпал, — и если это правило выключено
  (`checkstate="0"`), объект не рисуется вообще, к ветке ELSE он не
  переходит. Отсюда пропадали леса с `leaf_type`: ветки
  `leaf_type='needleleaved'/'broadleaved'/'mixed'` в стиле слоя `wood`
  были выключены, и 2202 из 6141 лесных полигонов не рисовались. Чтобы
  стиль остался, а объекты уходили в ELSE, у выключенной ветки должен
  быть фильтр, который не совпадает (например, условие по переменной
  проекта), — гасить саму ветку недостаточно.
- **Океан определяется по незамкнутым линиям берега**: сторона воды ищется
  отступом от линии, взятая точка лежит строго внутри отступа, а часть
  области выбирается по «содержит». Замкнутые кольца coastline — это
  острова, и по ним сторона выходила неверной: в дельте Дуная океаном
  оказывался крошечный обломок у края области, и море не заливалось вовсе.
  Растворение океана с внутренними водами падало на невалидной геометрии —
  перед ним геометрию надо чинить (`core/coastline.py`).
- **GRASS переименовывает поля**: первый недопустимый символ → `x`, остальные
  → `_` (`name:ru` → `name_ru`, `@id` → `xid`). После `skeleton` имена
  восстанавливает `Pipeline._restore_field_names` (правило
  `_grass_field_name`). Растворение — по `@id`.
- **Порядок углов GDAL**: `SetSpatialFilterRect` принимает
  `(minx, miny, maxx, maxy)`, а `GetEnvelope()` отдаёт
  `(minx, maxx, miny, maxy)`. Не смешивать; отбор полигонов — через
  `terrain.py: _PolygonIndex`.
- **Драйвер OSM читается датасетным API**: объекты забираются
  `dataset.GetNextFeature(include_layer=True)` — драйвер сам переключает
  слои и разбирает файл потоково (GDAL ≥ 3.6). Опрос слоёв по кругу
  (`INTERLEAVED_LAYER_ORDER`) работает только на маленьких выгрузках: на
  больших очередь слоя переполняется (в GDAL 100000 объектов), драйвер
  обрывает чтение, и линии с мультиполигонами теряются целиком.
- **Полигональная запись SQLite не сжимает геометрию**:
  `COMPRESS_GEOM=YES` вместе с `SPATIALITE=YES` меняет топологию
  полигонов (появляются самопересечения), и `native:difference`
  пропускает объект из `water_dissolved` с ERROR «некорректная
  геометрия». Сжатие из `save_vector` убрано. Дополнительно после
  `dissolve`/`singleparts` в рецептах `water`/`water_intermittent` стоит
  `fix()`, а сырые полигоны `bare_rock`/`scree` чинятся в начале рецепта.
- **Запросы по членам отношений в PBF не поддерживаются**: `r.relations`
  (`place_admin_centre_*`) драйвер не отдаёт, поэтому в списке запросов
  по умолчанию их нет. Грубый фильтр по области и объединение выгрузок —
  ожидаемые информационные заметки (`PbfDataset.notes`), а не warnings.
- **Замкнутые coastline-way внутри мультиполигона драйвер отдельно не
  отдаёт**: у группы островов остаётся только relation (например,
  `place=archipelago`). Поэтому `resources/queries/island.txt` включает
  архипелаги, иначе острова не попадают в `island.sqlite`, не вычитаются из
  океана и остаются под водой.
- **Фильтр на `points` действует на все слои** и теряет вершины больших
  отношений. Поэтому `_apply_spatial_filter` ставит фильтр на все слои, кроме
  `points`; точная отсечка — при разборе. Цена — примерно в 4 раза больше
  времени на чтение PBF.
- **Склейка osmium `merge` оставляет все версии объекта**: GDAL читает
  обычный OSM-файл и обрывается на повторяющихся id (иногда пустым
  `RuntimeError`). Поэтому `osmium_prefilter._merge_files` вызывает
  `apply-changes`, а не `merge`: он оставляет последнюю версию каждого
  объекта. Если склейка всё же не читается, `sources.py: prepare_sources`
  читает карты по отдельности, дубликаты отсекаются по `@id`. Если osmium
  уже вернул отдельные пути, откат всё равно обязан вызвать
  `prepare_dataset(use_osmium=False)`: иначе он снова склеит файл и упадёт
  на том же месте. `_iter_features` добавляет в ошибку число объектов и
  слой, чтобы пустое сообщение GDAL было диагностируемым.
- **`osmium extract`**: `-b <padded bbox> --strategy=smart -S types=any`;
  запас `padded_bbox` — 0.3° или 15% от области. `smart` не берёт отношения
  вне области, их добирает `tags-filter` по `COVERING_EXPRESSIONS` (горные
  массивы и хребты). Вырезка области и поиск горных массивов всех карт
  идут параллельно (`ThreadPoolExecutor`, число процессов — 3/4 ядер,
  `core/cpu.py`) — каждая операция читает исходную карту независимо,
  результат тот же. Вырезанные области нескольких карт склеиваются
  `osmium merge` **после** вырезки, иначе разорванные границей отношения не
  собрать.
- **Файлы горных массивов читаются без фильтра** (`unfiltered`): их геометрия
  лежит вне области, и фильтр отбросил бы их целиком.
- **Откат чтения** (фильтр не доставил область → файл читается целиком)
  обрезает записи только текущего файла по смещению, а не всех.
- Бинарь в zip теряет бит исполнения — `osmium_tool.py: ensure_executable`;
  имя файла ровно `osmium` (osmium воспринимает его как имя команды).
- Полнота проверяется `tools/check_pbf_coverage.py`: эталон — osmium,
  сравнение множеств `@id`. Известный остаток ~0,06% на границе области;
  увеличение запаса фильтра не помогает.

## Проверка в реальном QGIS

- Offscreen-тесты не покрывают регистрацию плагина и раскладку окон.
- **Пустой `processing/` в корне репозитория** (его создаёт QGIS)
  Python принимает за namespace-пакет: `import processing` проходит, а
  `processing.core` — нет. `pipeline._load_processing()` ставит путь QGIS
  в начало `sys.path` и сбрасывает уже импортированный пустой пакет.
  Каталог в `.gitignore`, удалять его не обязательно.
- Не трогать работающий QGIS (`pgrep -x qgis.bin`); запускать с временным
  профилем: `qgis --profiles-path /tmp/... --code script.py`.
- **Offscreen-рендер карты** для проверки стиля на реальных данных:
  ```python
  import sys
  sys.path.insert(0, '.')
  import tests
  from tests import qgis_app
  app = qgis_app()
  from qgis.core import (
      QgsProject, QgsMapSettings, QgsMapRendererCustomPainterJob,
      QgsRectangle, QgsCoordinateReferenceSystem, QgsCoordinateTransform,
  )
  from qgis.PyQt.QtGui import QImage, QPainter, QColor
  from qgis.PyQt.QtCore import QSize
  from qgis_xtopo.core.resources import template_path

  project = QgsProject.instance()
  project.read(str(template_path()))  # только str, не Path
  layer = next(
      item for item in project.mapLayers().values()
      if item.name() == 'railway all'
  )
  # В шаблоне путь ./vector/...; подменяем на реальный файл.
  layer.setDataSource('/path/to/vector/railway_all.sqlite',
                      layer.name(), 'ogr')
  layer.reload()

  settings = QgsMapSettings()
  settings.setLayers([layer])
  settings.setDestinationCrs(QgsCoordinateReferenceSystem('EPSG:3857'))
  settings.setExtent(QgsCoordinateTransform(
      QgsCoordinateReferenceSystem('EPSG:4326'),
      settings.destinationCrs(), project.transformContext(),
  ).transformBoundingBox(QgsRectangle(8.3, 46.8, 8.6, 47.0)))
  settings.setOutputSize(QSize(1000, 700))
  settings.setBackgroundColor(QColor('white'))

  image = QImage(settings.outputSize(), QImage.Format_ARGB32)
  image.fill(QColor('white'))
  painter = QPainter(image)
  job = QgsMapRendererCustomPainterJob(settings, painter)
  job.start()
  job.waitForFinished()
  painter.end()
  image.save('/mnt/data/temp/map.png')
  ```
  `setExtent` ждёт extent уже в целевой CRS, поэтому пересчитывать его
  нужно через `QgsCoordinateTransform`. У `QgsRectangle` нет `combine`
  и `united` — объединять через `combineExtentWith`. Готовый PNG класть
  в `/mnt/data/temp`, не в репозиторий. Рабочие данные пользователя
  можно читать, но не изменять.
- Панель открывается при `QGIS_XTOPO_OPEN=1`; показ — по
  `iface.initializationCompleted`, иначе восстановление окон перезапишет
  `show()`.
- Плагин включается секцией `[PythonPlugins]` в `QGIS/QGIS3.ini` профиля
  (не `[Plugins]`). В `qgis.utils` QGIS 3.44 нет `enabled_plugins`.

## Проверка положения пиков OSM

- `tools/check_peak_placement.py` ищет `natural=peak` без названия, стоящие
  не на вершине и не на хребте. Проверяются только пики без тегов `name` и
  `name:xx`; с `ele` и без — две разные категории в отчёте.
- **Источник рельефа выбирается `--dem-source`**: поддерживаются все наборы
  плагина (`srtm`, `cop30`, `nasadem`, `alos`, `3dep`, `manual`). Растровые
  наборы скачиваются через `core.terrain.download_cog_dem` и приводятся к
  сетке 1″ в EPSG:4326, поэтому метрики сравнимы с SRTM. Для `manual` или
  своего файла — `--dem-file`.
- **Для ALOS, Copernicus и NASADEM включается профиль порогов**
  (`SOURCE_THRESHOLD_PROFILES`): их поверхность сдвигает метрики
  относительно SRTM, и базовое правило даёт 6–10 ложных срабатываний на
  95 верных пиках. Профиль поднимает `no_crest_450` (40→80),
  `far_drop` (240→260), `near_max_d` (300→400 у ALOS/Copernicus),
  `summit_far_neighbour` (600→900), `ele_below` (4→4.6) и опускает
  `stream_distance` (200→50). У NASADEM `near_max_d` остаётся 300, а
  первая конъюнкция требует, чтобы вершина была дальше 100 м
  (`valley_summit_min`, аргумент `--valley-summit`). На ручной разметке:
  SRTM 0 ложных / 46 из 49, ALOS 0 / 37, Copernicus 2 / 38,
  NASADEM 1 / 39. `--no-source-profile` возвращает базовое правило;
  `3dep` и `manual` профиль не получают.
- **Правило — ИЛИ конъюнкций**: ошибка отмечается, если сработала хотя бы
  одна пара признаков. Одиночное условие не годится — «нет острого гребня
  в 100 м» срабатывает и на настоящих круглых вершинах.
- **В пайплайне правило применяется автоматически** после рельефа
  (`core/peak_filter.py`): безымянные пики с вердиктом `error` удаляются из
  `peak.sqlite`, у остальных безымянных пиков `ele` заменяется на высоту
  рельефа при расхождении больше 10 %. Конъюнкция 11 (`ele_diff`) при
  удалении отключена: расхождение высоты — повод исправить `ele`, а не
  удалить пик. Для SRTM окна читаются из кэша `.hgt` (та же сетка, что у
  инструмента), для остальных источников — из `merged_dem.tif`. Краткая
  статистика выводится в журнал.
- **Метрики пиков считаются параллельно.** Растр проекта в сетке 1″
  целиком читается в память (`ProjectDem.prepare_shared`, до 24 млн
  пикселей; массив только читается), и окна `peak_placement.measure`
  считаются в нескольких потоках (3/4 ядер, но не больше 4) — результат
  от порядка не зависит. Больше четырёх потоков упираются в GIL и
  работают медленнее. Для SRTM-кэша и крупных растров путь прежний,
  последовательный. `flow_accumulation` вместо поячеечного цикла считает
  адрес стока векторно и ведёт накопление списком Python; алгоритм обязан
  совпадать с прежним — проверка `FlowAccumulationTest` в
  `tests/test_pipeline_logic.py` сверяет с эталонной реализацией.
- **`ele` у точек сохраняется только с `osmconf.ini` без `ele` в `ignore`**
  (`pbf_source.ensure_osm_config`): стандартный конфиг GDAL выбрасывает
  тег, и подписи высот не работают.
- Признаки — по выбранному рельефу и высоте из тега OSM `ele`: гребень
  (выпуклость поперёк склона на нескольких масштабах), водораздел (площадь
  водосбора D8), поперечный профиль склона, кольцо вокруг точки, ближайший
  локальный максимум, кривизна, расхождение `ele` и DEM.
- **Рельеф — это SRTM v3 (AWS `elevation-tiles-prod/skadi`), не SRTM1.**
  Кэш плагина и тайлы skadi байт-в-байт одни данные. Завышение DEM в
  Гималаях — свойство самих данных, а не артефакт заполнения пустот.
  Copernicus GLO-30 хуже: разброс расхождения с OSM `ele` −15…+30 % против
  −8…+11 % у SRTM v3. Менять источник DEM смысла нет.
- **Геометрию водных объектов OSM для правила не использовать:** ручьи
  проведены по-разному, признак получается ненадёжным (пользователь так
  решил после того, как метрика расстояния до ручья дала хороший результат
  на одной выборке).
- **Два разных признака «ближайшая вершина»: `summit_*` считается по сырому
  DEM, `near_max_*` — по сглаженному.** В сетке перебора был только
  сглаженный, и грубые пики в пологом рельефе терялись. Оба нужны.
- **В Гималаях DEM завышен на сотни метров** (у 43 % пиков DEM выше OSM
  `ele`): абсолютные пороги в метрах там не работают. Часть признаков
  нормирована на местный рельеф, сверка `ele` с DEM вынесена в отдельный
  признак.
- Пороги перебираются перебором по размеченной вручную выборке: цель —
  ноль ложных срабатываний на «верных» пиках при максимуме пойманных
  «ошибочных». Правку порогов проверять на всей выборке сразу: на одном
  регионе легко поймать лишнее.
- **При поиске конъюнкций важно пересечение, а не каждое условие
  по отдельности.** Одиночное условие, задевающее верные пики, в паре с
  другим может дать ноль ложных. Если отбрасывать такие условия сразу,
  теряется большая часть кандидатов и качество правила падает (на разметке
  95 верных / 49 ошибочных это стоило 3 пойманных пика).
- Переносить правило из настройки в инструмент нужно пошагово: сверить
  значения метрик (инструмент и настройка обязаны считать одинаково) и
  пороги конъюнкций. Один и тот же признак может входить в разные
  конъюнкции с разными порогами — для каждой свой аргумент.
- Шапка CSV и строка должны иметь одинаковое число полей, иначе значения
  разъезжаются по столбцам и отчёт врёт. В `write_reports` стоит проверка.
- `tools/render_peak_review.py` рисует фрагменты карты по CSV, рендер
  параллельный (`--jobs`). `tools/make_peak_map.py` собирает интерактивную
  карту; `--csv` можно указать несколько раз — регионы сводятся на одной
  карте.
- Материалы проверки лежат в `~/qgis_projects/peak_review_<регион>/`,
  размеченные вручную пики — в `~/qgis_projects/peak_review_labels/`
  (каталог `/tmp` очищается, метки там теряются).

## Стиль изменений

- В этом проекте комментарии, docstring'и и сообщения — на русском, как в
  окружающем коде (это переопределяет общее правило про английский).
- UI-строки пишутся по-русски; английский — в `resources/lang/en.json`
  (словарь «русская строка → английская», работает в обе стороны). Уже
  построенные виджеты переводит `gui/translation.py`.
- Тесты добавлять в существующие тематические файлы. Запуск — только через
  `./tools/run_tests.sh`.
- После изменения поведения обновляйте docstring'и и README (разделы
  «Установка» и «Разработка»).
